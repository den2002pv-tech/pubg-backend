# Инструкции для ИИ-разработчика

## Назначение проекта

Проект — приложение для управления коллекцией и обмена картами PUBG Mobile. Пользователь может сканировать скриншоты, вести инвентарь карт, отмечать недостающие карты и управлять списком «Ищу». В проекте также есть серверная часть и инструменты администратора для работы с распознаванием карт и иконками.

Проект находится на этапе тестирования. Базы данных пока не содержат реальных пользовательских данных. Не нужно сохранять обратную совместимость со старой тестовой схемой любой ценой: если изменение схемы, структуры данных или API улучшает архитектуру и исправляет ошибки, можно менять их напрямую. Перед разрушительными действиями всё равно убедись, что затронуты только тестовые данные и тестовые ресурсы.

Перед изменениями обязательно изучай актуальный код репозитория: не считай этот файл полной документацией архитектуры.

## Обязательные правила работы

1. Сначала проверь структуру репозитория, текущую ветку, связанные функции и имеющиеся тесты.
2. Делай целевые изменения. Не переписывай целиком большие файлы, если достаточно изменить конкретную функцию, но не сохраняй неудачную архитектуру только ради минимального diff.
3. Не утверждай, что тесты или приложение проверены, если соответствующие проверки действительно не запускались.
4. После изменения кратко сообщай: какие файлы изменены, что сделано, какие проверки выполнены и что осталось проверить.
5. Если обнаружена неоднозначность, которая может привести к потере данных или изменению поведения, сначала изучи код и окружение. Если есть подтверждение, что база/ресурс содержит только тестовые данные, допустимы пересоздание схемы, очистка тестовых данных и другие необходимые для разработки изменения.

## Инвентарь и список «Ищу»

- Сохраняй корректную связь между пользователем, картой и количеством экземпляров.
- Повторное сканирование одной и той же коллекции не должно создавать лишние записи или терять уже сохранённые данные без предусмотренной логики.
- Если в инвентаре количество карты больше нуля, карта не должна оставаться в списке «Ищу», если текущая бизнес-логика не предусматривает отдельное исключение.
- Карты, которых нет в инвентаре, и карты в списке «Ищу» — разные понятия. Не объединяй эти состояния.
- Дубликаты определяй по устойчивому идентификатору карты и пользователю, а не по порядку обнаружения, позиции на экране или похожему тексту.
- При изменении фильтров, сортировки, счётчиков или отрисовки проверяй взаимосвязанные состояния: инвентарь, недостающие карты, список «Ищу» и дубликаты.
- Если текущая модель ID приводит к ошибкам, её можно изменить вместе с зависимыми участками кода и тестовой схемой БД. Обнови все места использования ID и добавь/исправь тесты.

## База данных и схема

- Проверяй все места, которые используют изменяемые таблицы, столбцы, индексы и запросы.
- На этапе тестирования разрешено менять схему БД напрямую, переименовывать и удалять столбцы/таблицы, менять связи и пересоздавать тестовую базу, если это нужно для правильной архитектуры.
- Не трать время на поддержку старой схемы или сложные миграции только ради совместимости с предыдущими тестовыми версиями. Выбирай простой и надёжный путь для текущего проекта.
- Перед очисткой, пересозданием или удалением данных проверь, что используемая база и ресурсы действительно тестовые. Если окружение неясно, сначала выясни это, а не удаляй данные вслепую.
- Проверяй граничные значения: отсутствующая запись, количество 0, положительное количество, повторная операция и неизвестный ID.
- Автоматические тесты должны использовать отдельную тестовую базу или изолированные данные.

## Сканирование и распознавание изображений

- Учитывай, что скриншоты могут иметь разное разрешение, масштаб и расположение элементов.
- При изменении обрезки изображения проверяй, что важные элементы счётчика не обрезаются и что отсутствие счётчика корректно обрабатывается.
- Не считай две карты одинаковыми только потому, что у них похожие префиксы хэша. Используй предусмотренный алгоритм сравнения и его пороги.
- Различай постоянные иконки, временные файлы и результаты распознавания; не удаляй постоянные данные при очистке временных файлов.
- При изменении алгоритма распознавания проверяй как успешные совпадения, так и случаи, когда совпадения нет или оно неоднозначно.

## Интерфейс и API

- Проверяй согласованность интерфейса, API и серверных ответов. На этапе тестирования можно менять API-контракты, если одновременно обновить все зависимые части проекта.
- При изменении кнопок, фильтров, модальных окон или событий проверь все связанные обработчики и состояния загрузки/ошибки.
- Предусматривай понятные пустые состояния, сообщения об ошибках и подтверждения для массовых или потенциально необратимых действий.
- Не оставляй дублирующиеся HTML-элементы с одинаковыми ID.
- Избегай обработчиков событий, которые могут добавляться повторно при каждом обновлении интерфейса.
- Не скрывай ошибки сервера так, чтобы пользователь видел сообщение об успешном сохранении, когда сохранение не выполнено.

## Безопасность и секреты

- Никогда не добавляй пароли, токены, ключи API, cookie, секреты сессий или реальные пользовательские данные в код, тесты, коммиты и логи.
- Используй переменные окружения для секретов и не выводи их значения в журнал.
- Сохраняй проверки авторизации и прав доступа на сервере; не полагайся только на скрытие кнопок в браузере.
- Проверяй пользовательский ввод и обрабатывай ошибки безопасно.
- Не ослабляй авторизацию ради упрощения локального тестирования.
- Перед очисткой или изменением ресурсов Render, Vercel и GitHub проверяй, что выбран правильный проект, сервис, ветка и окружение. Не удаляй и не пересоздавай ресурсы инфраструктуры без необходимости для текущей задачи.

## Проверки перед завершением

1. Найди существующие инструкции запуска и тестирования; не выдумывай команды, если конфигурация проекта говорит иначе.
2. Для Python-кода запускай доступную проверку синтаксиса и релевантные тесты.
3. Для JavaScript проверь синтаксис и затронутые сценарии. Если проверка браузера недоступна, явно укажи это.
4. Для изменений БД проверь соответствующие SQL-операции на тестовой базе. Если схема пересоздавалась, убедись, что приложение создаёт и использует новую схему корректно.
5. Для фильтров и коллекции проверь добавление карты, изменение количества, повторное сканирование, удаление из «Ищу» и пустые результаты.
6. Просмотри итоговый diff и убедись, что в коммит не попали временные файлы, архивы, секреты или несвязанные изменения.

Если в репозитории пока нет автоматических тестов, не заявляй, что тесты прошли. Предложи добавить небольшие тесты для изменённого поведения.

## Стиль изменений

- Используй существующие соглашения проекта и зависимости, не добавляй библиотеку без необходимости.
- Не сохраняй старые имена функций, API-поля, таблиц или столбцов только ради совместимости, если они мешают исправлению архитектуры. Обновляй все связанные участки кода и тесты согласованно.
- Комментарии добавляй для нетривиальных решений, а не для очевидных строк.
- Не включай в один коммит несвязанные рефакторинги.
- Не создавай фиктивные данные или результаты проверок для отчёта.
