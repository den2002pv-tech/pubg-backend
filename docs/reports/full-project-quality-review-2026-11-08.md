## 4. Findings

### F-01 — ForceReply regex: исправлено в feature branch

**Статус:** RESOLVED / CONFIRMED  
**Компонент:** Telegram exchange code  
**Файл:** `trade_requests.py`, функция `_handle_exchange_code_reply`

В текущей ветке используется regex:

```python
r"Введите код обмена для заявки #(\d+) в ответ на это сообщение\..*"
```

Он соответствует prompt с номером заявки и дополнительным текстом. Тест `test_telegram_webhook_delivers_code_from_force_reply` прошёл в CI. Поэтому прежний дефект из аудита `main` не переносится в список активных проблем этой ветки.

**Остаток:** добавить отрицательные тесты на неправильный prompt, отсутствующий номер и несоответствие отправителя/чата. Текущая реализация уже проверяет приватный чат и совпадение Telegram ID отправителя с chat ID.

### F-02 — Буквальные `\\n` в Telegram-сообщениях

**Severity:** MEDIUM  
**Confidence:** CONFIRMED  
**Файлы:** `trade_requests.py`, ориентировочно строки 689–692 и 783  
**Компоненты:** `/help`, prompt кода обмена

В обычных строковых литералах используются двойные обратные слеши перед `n`. В runtime это превращается в буквальные символы `\n`, а не в перенос строки.

Проверенные места:
- текст команды `/help`;
- prompt «Введите код обмена для заявки…».

Тест команды проверяет отсутствие буквального `\\n` только для `/start`; он не защищает от регрессии в `/help`. Для callback prompt отдельная проверка runtime-переносов также необходима.

**Влияние:** пользователи могут видеть служебную последовательность `\n` в сообщении вместо форматированного текста. Regex ForceReply при этом может продолжать работать, потому что он допускает дополнительный текст после первой строки.

**Рекомендация:** заменить только ошибочные строковые escape-последовательности на реальные переводы строк; добавить тесты runtime payload для `/help` и callback prompt.

### F-03 — Конкурентная перезапись каталога при регенерации хэшей

**Severity:** MEDIUM  
**Confidence:** POTENTIAL  
**Файлы:** `main.py`, `load_db()`, `save_db()`, `_regenerate_hashes_from_icons()`, admin CRUD

`save_db()` атомарно заменяет JSON-файл через временный файл, но общей блокировки чтения-модификации-записи каталога не обнаружено. Фоновая регенерация загружает снимок каталога, обрабатывает иконки и сохраняет этот снимок позже. В это время административный endpoint может сохранить более свежую версию каталога.

При определённом порядке операций старый снимок регенерации может перезаписать свежие изменения. Сценарий не воспроизводился, поэтому это риск, а не подтверждённая потеря данных.

**Рекомендация:** ввести общую синхронизацию для всех операций изменения каталога либо optimistic version check. Проверить конкурентное редактирование, удаление карты/иконки и регенерацию. Учесть, что lock в памяти одного worker не защищает от нескольких процессов.

### F-04 — Нет ограничения попыток входа в админку на уровне приложения

**Severity:** MEDIUM  
**Confidence:** POTENTIAL  
**Файл:** `main.py`, `admin_login()`, ориентировочно строки 1674–1685

Обработчик `POST /admin/login` сравнивает пароль через `hmac.compare_digest()`, но не содержит счётчика попыток, задержки или временной блокировки.

Настройки reverse proxy и rate limiting на Enzonic/Render не проверялись. Поэтому нельзя утверждать, что endpoint доступен для неограниченного подбора в production, но защита на уровне приложения не обнаружена.

**Рекомендация:** сначала проверить внешние ограничения. Если их нет, добавить распределённый или инфраструктурный rate limit, не полагаясь на локальный словарь процесса.

### F-05 — Health endpoint проверяет только доступность HTTP-процесса

**Severity:** INFO  
**Confidence:** CONFIRMED  
**Файл:** `main.py`, строки 1396–1398

`GET /health` возвращает статический `{"status":"ok"}` и не проверяет PostgreSQL.

В `README_DEPLOY.md` это ограничение уже описано: endpoint подтверждает доступность HTTP-процесса, но не исправность БД и бизнес-функций. Поэтому это не противоречие реализации и документации, если endpoint используется как liveness probe.

**Рекомендация:** если платформа использует его для readiness, добавить отдельный ограниченный по времени readiness endpoint с проверкой БД. Не выполнять SQL-проверку на каждый частый liveness probe.

### F-07 — Отслеживаемые Python bytecode-файлы

**Severity:** LOW  
**Confidence:** CONFIRMED  
**Файлы:** `__pycache__/*.pyc`, `tests/__pycache__/*.pyc`

В Git tree присутствуют 10 файлов `.pyc` в двух каталогах `__pycache__`. Правила `.gitignore` уже исключают `__pycache__/` и `*.pyc`, но не удаляют ранее отслеживаемые файлы.

**Рекомендация:** удалить эти генерируемые файлы из Git отдельным контролируемым изменением. Не удалять локальные файлы пользователя; проверить, что в commit попадают только tracked bytecode paths.

### F-08 — Scan rate limit локален для процесса

**Severity:** MEDIUM  
**Confidence:** CONFIRMED (ограничение реализации); эксплуатационный эффект зависит от числа worker  
**Файл:** `main.py`, `SCAN_RATE_LIMIT_EVENTS` и `_enforce_scan_rate_limit()`, строки около 59 и 1250–1275

Счётчики лимита хранятся в глобальном словаре Python-процесса. При нескольких worker каждый процесс имеет независимый счётчик. В результате суммарный допустимый поток запросов может быть выше настроенного значения, если приложение работает в нескольких процессах.

**Рекомендация:** явно зафиксировать однопроцессный режим либо перенести ограничение в общий backend (например, Redis/reverse proxy). Не добавлять новую инфраструктурную зависимость без подтверждения конфигурации хостинга.

### F-09 — Зависимости backend не закреплены

**Severity:** LOW / INFO  
**Confidence:** CONFIRMED  
**Файлы:** `requirements.txt`, `requirements-dev.txt`

Основные production зависимости перечислены без фиксированных версий. Для pytest задан диапазон, но lock-файла или полного constraints-файла не обнаружено.

**Влияние:** одинаковый commit может устанавливаться с разными версиями библиотек в разные даты, что снижает воспроизводимость сборок.

**Рекомендация:** определить поддерживаемые версии Python и библиотек, добавить lock/constraints-процесс и регулярно обновлять зависимости через контролируемые PR с CI.

### F-10 — Предупреждения GitHub Actions о runtime Node.js

**Severity:** INFO  
**Confidence:** CONFIRMED  
**Файл:** `.github/workflows/*.yml`

CI завершился успешно, но логи содержат предупреждения о переходе actions с Node.js 20 на Node.js 24, а также предупреждение Node.js о deprecated-модуле `punycode`.

## 5. Безопасность, приватность и производительность

### Что подтверждено статическим просмотром

- Telegram Mini App initData проверяется через HMAC.
- Webhook сверяет `X-Telegram-Bot-Api-Secret-Token` с `TELEGRAM_WEBHOOK_SECRET`.
- Admin session подписывается HMAC; сравнение выполняется через `hmac.compare_digest()`.
- Загрузка скриншота ограничена 15 MiB и 30 мегапикселями.
- Для сканирования есть semaphore/concurrency limit, лимит запросов и отдельные настройки потоков OpenCV.
- Аналитика использует allowlist событий и фильтрует набор свойств.
- В проверенных шаблонах ключевые динамические значения имени игрока, имени карты и ID в пользовательских торговых карточках проходят HTML escaping.
- Код обмена не записывается в таблицу как отдельное значение; отправка выполняется через Telegram API.

### Что требует дополнительной проверки

- Rate limit для входа администратора и общий rate limit между worker.
- Секреты и история репозитория: полный secret scanning не выполнялся.
- Dependency vulnerability audit не выполнялся.
- Настройки cookies/headers/TLS и reverse proxy нельзя подтвердить по исходникам.
- Не проводились внешние security-тесты.
- Не проверялась фактическая доставка Sentry events.
- Не проводились контролируемые CPU/RAM/load benchmarks.
- Не проверялись реальные retention и очистка PostgreSQL analytics events в production.
