## 4. Findings

### F-01 — ForceReply regex: исправлено в feature branch

**Статус:** RESOLVED / CONFIRMED  
**Компонент:** Telegram exchange code  
**Файл:** `trade_requests.py`, функция `_handle_exchange_code_reply`

В текущей ветке используется regex:

```python
r"Введите код обмена для заявки #(\d+) в ответ на это сообщение\..*"
```

Он соответствует prompt с номером заявки и дополнительным текстом. Тест `test_telegram_webhook_delivers_code_from_force_reply` прошёл в CI. Поэтому прежний дефект из аудита `main` не переносится в список активных проблем этой ветки.

**Остаток:** добавить отрицательные тесты на неправильный prompt, отсутствующий номер и несоответствие отправителя/чата. Текущая реализация уже проверяет приватный чат и совпадение Telegram ID отправителя с chat ID.

### F-02 — Буквальные `\\n` в Telegram-сообщениях

**Severity:** MEDIUM  
**Confidence:** CONFIRMED  
**Файлы:** `trade_requests.py`, ориентировочно строки 689–692 и 783  
**Компоненты:** `/help`, prompt кода обмена

В обычных строковых литералах используются двойные обратные слеши перед `n`. В runtime это превращается в буквальные символы `\n`, а не в перенос строки.

Проверенные места:
- текст команды `/help`;
- prompt «Введите код обмена для заявки…».

Тест команды проверяет отсутствие буквального `\\n` только для `/start`; он не защищает от регрессии в `/help`. Для callback prompt отдельная проверка runtime-переносов также необходима.

**Влияние:** пользователи могут видеть служебную последовательность `\n` в сообщении вместо форматированного текста. Regex ForceReply при этом может продолжать работать, потому что он допускает дополнительный текст после первой строки.

**Рекомендация:** заменить только ошибочные строковые escape-последовательности на реальные переводы строк; добавить тесты runtime payload для `/help` и callback prompt.

### F-03 — Конкурентная перезапись каталога при регенерации хэшей

**Severity:** MEDIUM  
**Confidence:** POTENTIAL  
**Файлы:** `main.py`, `load_db()`, `save_db()`, `_regenerate_hashes_from_icons()`, admin CRUD

`save_db()` атомарно заменяет JSON-файл через временный файл, но общей блокировки чтения-модификации-записи каталога не обнаружено. Фоновая регенерация загружает снимок каталога, обрабатывает иконки и сохраняет этот снимок позже. В это время административный endpoint может сохранить более свежую версию каталога.

При определённом порядке операций старый снимок регенерации может перезаписать свежие изменения. Сценарий не воспроизводился, поэтому это риск, а не подтверждённая потеря данных.

**Рекомендация:** ввести общую синхронизацию для всех операций изменения каталога либо optimistic version check. Проверить конкурентное редактирование, удаление карты/иконки и регенерацию. Учесть, что lock в памяти одного worker не защищает от нескольких процессов.

### F-04 — Нет ограничения попыток входа в админку на уровне приложения

**Severity:** MEDIUM  
**Confidence:** POTENTIAL  
**Файл:** `main.py`, `admin_login()`, ориентировочно строки 1674–1685

Обработчик `POST /admin/login` сравнивает пароль через `hmac.compare_digest()`, но не содержит счётчика попыток, задержки или временной блокировки.

Настройки reverse proxy и rate limiting на Enzonic/Render не проверялись. Поэтому нельзя утверждать, что endpoint доступен для неограниченного подбора в production, но защита на уровне приложения не обнаружена.

**Рекомендация:** сначала проверить внешние ограничения. Если их нет, добавить распределённый или инфраструктурный rate limit, не полагаясь на локальный словарь процесса.

### F-05 — Health endpoint проверяет только доступность HTTP-процесса

**Severity:** INFO  
**Confidence:** CONFIRMED  
**Файл:** `main.py`, строки 1396–1398

`GET /health` возвращает статический `{"status":"ok"}` и не проверяет PostgreSQL.

В `README_DEPLOY.md` это ограничение уже описано: endpoint подтверждает доступность HTTP-процесса, но не исправность БД и бизнес-функций. Поэтому это не противоречие реализации и документации, если endpoint используется как liveness probe.

**Рекомендация:** если платформа использует его для readiness, добавить отдельный ограниченный по времени readiness endpoint с проверкой БД. Не выполнять SQL-проверку на каждый частый liveness probe.

### F-06 — Документация расходится с screenshot fixtures и тестами

**Severity:** LOW  
**Confidence:** CONFIRMED  
**Файлы:** `docs/scanning-regression.md`, `docs/development.md`, `tests/fixtures/screenshots/README.md`, `tests/test_screenshot_fixtures.py`

В `docs/scanning-regression.md` указаны старые показатели: 21 скриншот, 73 области, 69 `owned` и 4 `unowned`. Текущий манифест содержит 25 скриншотов, 85 областей, 81 `owned` и 4 `unowned`; у всех 81 owned-областей `identity_verified=true`.

Документ также утверждает, что `card_id`/`card_name` используются только для диагностики и что текущий тест проверяет лишь геометрию и количество. Фактически отдельный тест `test_verified_screenshot_card_identities_match_catalog` проверяет сопоставление подтверждённых ID с каталогом.

`docs/development.md` содержит ещё более существенный устаревший текст: утверждает, что манифест пуст, а `unowned`-области не проверяются. В актуальном `tests/test_screenshot_fixtures.py` есть проверки размеченных случаев, исключения `unowned`-областей и подтверждённых идентичностей.

**Влияние:** разработчик получает неверное представление о покрытии и может не использовать уже имеющиеся регрессионные проверки либо недооценить их фактический объём.

**Рекомендация:** синхронизировать оба документа с тестами и манифестом. Добавить автоматическую проверку ключевых чисел/утверждений либо заменить жёсткие числа на динамически генерируемую сводку. Считать README fixtures источником формата, но сверять его с исполняемыми тестами.

### F-07 — Отслеживаемые Python bytecode-файлы

**Severity:** LOW  
**Confidence:** CONFIRMED  
**Файлы:** `__pycache__/*.pyc`, `tests/__pycache__/*.pyc`

### F-08 — Scan rate limit локален для процесса

**Severity:** MEDIUM  
**Confidence:** CONFIRMED (ограничение реализации); эксплуатационный эффект зависит от числа worker  
**Файл:** `main.py`, `SCAN_RATE_LIMIT_EVENTS` и `_enforce_scan_rate_limit()`, строки около 59 и 1250–1275

Счётчики лимита хранятся в глобальном словаре Python-процесса. При нескольких worker каждый процесс имеет независимый счётчик. В результате суммарный допустимый поток запросов может быть выше настроенного значения, если приложение работает в нескольких процессах.

**Рекомендация:** явно зафиксировать однопроцессный режим либо перенести ограничение в общий backend (например, Redis/reverse proxy). Не добавлять новую инфраструктурную зависимость без подтверждения конфигурации хостинга.

### F-11 — Синхронный I/O и CPU-работа внутри async endpoints



**Severity:** MEDIUM  

**Confidence:** CONFIRMED (механизм блокировки event loop подтверждён кодом; фактическая деградация под нагрузкой не измерялась)  

**Файлы:** `main.py`, `trade_requests.py`, `database.py`, `analytics.py`



В ряде `async def`-маршрутов синхронные функции вызываются напрямую, без `asyncio.to_thread`, `anyio.to_thread.run_sync` или async-драйвера. Примеры:

- `GET /me/cards` (`main.py`, около 3590): синхронные `get_or_create_user`, `get_user_cards`, `get_desired_cards`.

- `GET /me/trade-matches`, `PUT /me/desired-cards`, `POST /me/trade-matches/.../contact` (`main.py`, около 3609–3732): синхронные PostgreSQL-запросы.

- `POST /me/trade-requests`, `GET /me/trade-requests`, `POST /me/trade-requests/{id}/{action}` (`trade_requests.py`, около 318–575): `_auth`, SQL, `_transition` и уведомления выполняются синхронно.

- `POST /telegram/webhook` (`trade_requests.py`, около 876–898): async endpoint вызывает обработчики, которые используют синхронный `urlopen` через `_telegram_call`.

- `POST /admin/screenshot-tests/preview` (`main.py`, около 2517–2570): после декодирования PNG через thread выполняет `scan_screenshot(...)` непосредственно в event loop.

- Административные endpoints тестовых фикстур вызывают синхронные GitHub HTTP-запросы из async handlers.



**Влияние:** пока синхронный SQL, сетевой вызов (таймаут Telegram до 8 секунд, GitHub до 30 секунд) или CV-обработка выполняются внутри event loop, другие запросы этого worker могут ожидать. Особенно чувствительны Telegram webhook, загрузка коллекции и обменные сценарии.



**Рекомендация:** системно разделить async boundary и blocking work: синхронный DB/API-код выполнять в thread pool либо перейти на согласованный async stack; CPU/CV и сетевые вызовы также выносить из event loop. Не оборачивать произвольные части транзакций независимо — сохранить целостность транзакции и порядок side effects. Добавить тест/benchmark конкурентной обработки лёгкого запроса при искусственно задержанном DB/Telegram вызове.



### F-12 — Код обмена отправляется в Telegram до commit PostgreSQL



**Severity:** MEDIUM  

**Confidence:** LIKELY  

**Файл:** `trade_requests.py`, `_deliver_exchange_code()`, около строк 575–646



Функция блокирует строку заявки через `SELECT ... FOR UPDATE`, затем отправляет код получателю через Telegram Bot API, и только после успешного ответа Telegram обновляет `exchange_code_sent_at` и выполняет `conn.commit()`.



Если Telegram принял сообщение, но HTTP-ответ потерялся/истёк по таймауту либо последующий UPDATE/commit завершился ошибкой, в БД может остаться `exchange_code_sent_at IS NULL`, хотя получатель уже получил код. Повторная отправка тогда может доставить тот же код ещё раз. Кроме того, row lock удерживается на всё время внешнего HTTP-вызова.



Существующий тест проверяет отказ Telegram API до фиксации статуса, но не моделирует ситуацию «Telegram принял сообщение — commit БД не состоялся». Проблема не воспроизводилась на реальном Telegram/PostgreSQL.



**Рекомендация:** определить семантику доставки при неопределённом результате внешнего запроса. Рассмотреть transactional outbox с ограниченным сроком хранения/шифрованием кода либо явное состояние `delivery_pending` и reconciliation-процесс. Не считать простое перемещение HTTP-вызова после commit полноценным решением: оно создаёт обратное окно — commit успешен, отправка не состоялась. Добавить тесты на потерю ответа и сбой commit.



### F-13 — Нет автоматического retention для analytics events



**Severity:** LOW / INFO  

**Confidence:** CONFIRMED (в приложении)  

**Файл:** `analytics.py`, `init_analytics_db()`, `record_analytics_events()`, `clear_scan_performance_metrics()`



Таблица `user_analytics_events` создаётся с `user_id` и `created_at`; события добавляются без срока хранения. Экспорт ограничивает выборку максимум 90 днями, но это ограничение экспорта, а не удаления данных. `clear_scan_performance_metrics()` удаляет только поля времени из JSON-свойств выбранных событий и не удаляет старые строки.



**Влияние:** объём таблицы растёт со временем, а история активности пользователей хранится без видимой в приложении границы. Внешняя политика очистки PostgreSQL/backup в Enzonic или Render не проверялась.



**Рекомендация:** определить и документировать срок хранения аналитики, добавить безопасную пакетную очистку старых строк и тест на cutoff/индексы. До проверки инфраструктурной политики не утверждать, что фактическое хранение бесконечно.
