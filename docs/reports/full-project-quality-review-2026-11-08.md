## 4. Найденные проблемы

### F-01 — HIGH / CONFIRMED
**Некорректный regex в обработчике Telegram ForceReply для кода обмена**

- Файл: `trade_requests.py`, примерно строка 731.
- Функция: `_handle_exchange_code_reply()`.
- Обнаруженный шаблон:
  ```python
  r"Введите код обмена для заявки #(\\d+) в ответ на это сообщение\\..*"
  ```
- Ожидаемое сообщение Telegram содержит обычный номер заявки и точку, а не буквальные обратные косые черты.
- CI падает на тесте `tests/test_trade_requests.py::test_telegram_webhook_delivers_code_from_force_reply`.
- Ожидалось: `[(29, 100, "ABC-123")]`.
- Фактически: `[]`.

**Влияние:** пользовательский сценарий передачи кода обмена через ответ на ForceReply не распознаёт корректное сообщение и не доставляет код в ожидаемый обработчик.

**Рекомендация:** исправить regex минимально, сохранив строгую проверку текста prompt и номера заявки. Добавить тесты на корректное сообщение, неверный номер и некорректный prompt.

### F-02 — MEDIUM / CONFIRMED
**Буквальные `\\n` в сообщениях Telegram вместо переносов строк**

- Файл: `trade_requests.py`.
- Примерные участки: строки 684, 689–692 и 783.
- В обычных Python-строках используется двойное экранирование, поэтому в runtime могут попасть два символа `\` и `n`, а не перевод строки.

**Влияние:** команды `/start`, `/help` и prompt кода обмена могут отображаться с буквальными `\\n`, ухудшая читаемость и потенциально ломая сопоставление prompt.

**Рекомендация:** заменить только ошибочные escape-последовательности на реальные переводы строк. Добавить проверки runtime-строк, не меняя корректные regex, JSON и другие намеренные escape-последовательности.

### F-03 — MEDIUM / POTENTIAL
**Возможная потеря обновлений каталога при конкурентном сохранении**

- Файл: `main.py`, примерно строки 4476–4515; связанные CRUD-операции около 4133–4186 и 4313–4328.
- Фоновая регенерация хэшей может прочитать каталог, долго обрабатывать его и сохранить весь устаревший снимок после того, как административная операция уже сохранила более свежие изменения.
- Общая синхронизация этих операций в просмотренном коде не обнаружена.

**Влияние:** при определённом порядке конкурентных операций возможна перезапись свежих данных каталога.

**Статус:** сценарий не воспроизводился; это риск, а не подтверждённая потеря данных.

**Рекомендация:** рассмотреть общий lock или optimistic version check и добавить тест конкурентного изменения каталога.

### F-04 — MEDIUM / POTENTIAL
**Не обнаружен app-level rate limit для `/admin/login`**

- Файл: `main.py`, примерно строка 1670.
- Проверка пароля использует `hmac.compare_digest()`, но ограничение количества попыток, progressive delay или временная блокировка в обработчике не обнаружены.

**Влияние:** при публичной доступности endpoint и отсутствии внешнего rate limit возможен подбор пароля.

**Ограничение:** настройки reverse proxy и хостинга не проверялись.

**Рекомендация:** проверить инфраструктурный rate limit и при необходимости добавить ограничение на уровне приложения с учётом нескольких worker-процессов.

### F-05 — LOW / CONFIRMED
**`/health` не проверяет доступность PostgreSQL**

- Файл: `main.py`, примерно строки 1396–1398.
- Endpoint возвращает статический `{"status":"ok"}`.

**Влияние:** если endpoint используется как readiness probe, приложение может сообщать о готовности при недоступной базе данных.

**Рекомендация:** разделить liveness и readiness. Проверка БД должна быть ограничена по времени и не создавать нагрузку на каждый частый probe.

### F-06 — LOW / CONFIRMED
**Устаревшие числа в документации регрессионных screenshot fixtures**

- Файл: `docs/scanning-regression.md`.
- Документация указывает 21 скриншот и 73 размеченные области (69 owned, 4 unowned).
- Манифест `tests/fixtures/screenshots/cases.json` содержит 25 скриншотов и 85 областей (81 owned, 4 unowned).

**Рекомендация:** обновить числа по фактическому манифесту и предусмотреть простой способ повторной сверки.

### F-07 — LOW / CONFIRMED
**В Git остаются отслеживаемые артефакты Python bytecode**

- В репозитории отслеживаются файлы `__pycache__` и `.pyc`, включая артефакты CPython 3.14.
- Правила исключения уже присутствуют в `.gitignore`, но не удаляют ранее отслеживаемые файлы автоматически.

**Рекомендация:** удалить только подтверждённые генерируемые артефакты из Git и проверить, что они исключены из будущих изменений.
