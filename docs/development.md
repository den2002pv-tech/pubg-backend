# Разработка и проверки

## Требования

Проект использует Python и FastAPI. Зависимости приложения перечислены в `requirements.txt`; тестовые зависимости — в `requirements-dev.txt`, который подключает основной файл и добавляет pytest.

В текущих GitHub Actions используются две версии Python:
- Python 3.12 в `.github/workflows/tests.yml`.
- Python 3.11 в `.github/workflows/counter-tests.yml`.

Для воспроизводимости запускайте проверки на версии, указанной в соответствующем workflow.

## Настройка окружения

Пример команд для Linux/macOS:

```sh
python -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements-dev.txt
```

В Windows активация виртуального окружения отличается; используйте команду активации для своего терминала.

Для запуска приложения требуется `DATABASE_URL`, указывающий на PostgreSQL. Не вставляйте строку подключения в исходники, тесты, shell-скрипты или логи. Для локальной разработки используйте отдельную тестовую базу. Не запускайте тесты с подключением к production-базе.

При локальном запуске FastAPI используйте ASGI-приложение `app` из `main.py`. Точную команду запуска и необходимые переменные окружения перед использованием сверяйте с актуальными конфигурациями развёртывания; репозиторий не должен предполагать наличие локальной БД по умолчанию.

## Проверки

Полный набор тестов (совпадает с основной CI-командой):

```sh
python -m pytest -q
```

Тесты каталога `tests` (совпадает с counter workflow):

```sh
python -m pytest -v tests
```

Проверка компиляции Python-файлов, используемая workflow:

```sh
python -m compileall -q main.py database.py scanner.py tests
```

Установка тестовых зависимостей выполняется через `requirements-dev.txt`. Если тесты не проходят, сначала выясните, ожидаем ли сбой из-за текущей реализации, окружения или эталонных данных. Не меняйте ожидаемые значения фикстур только ради зелёного CI.

## Регрессии счётчика

Перед изменением распознавания изучите:
- `scanner.py`;
- связанные обработчики в `main.py`;
- `tests/test_counter_fixtures.py` и `tests/test_counter_glyphs.py`;
- `tests/fixtures/counter/README.md`, `cases.json` и изображения в `tests/fixtures/counter/images/`.

В CI тесты запускаются в двух workflow, но это не означает, что локальные проверки или последний запуск CI уже успешны. После изменения проверьте фактический статус workflow на конкретном SHA.

## Git и безопасные изменения

1. Перед работой проверьте текущую ветку, HEAD и незакоммиченные изменения в доступном Git-окружении. Если используется только GitHub API, честно укажите, что локальный статус недоступен.
2. Рабочая ветка по текущим инструкциям — `feature/card-counter`; не делайте прямых изменений в `main`.
3. До коммита просмотрите список файлов и diff.
4. Не включайте временные изображения, логи, секреты и несвязанные рефакторинги.
5. При изменении схемы проверьте все места чтения/записи и ограничения. Удаление данных разрешено только после проверки, что они тестовые.
6. После отправки изменений проверьте SHA коммита и состояние соответствующих CI workflow, если эти данные доступны.

## Что обязательно проверять для связанных изменений

- **Инвентарь:** добавление карты, изменение количества, повторное сканирование, отсутствие отрицательных количеств и согласованность со списком «Ищу».
- **Обмены:** оба участника, право отправить код, повторная отправка, завершение без кода, двойное подтверждение, атомарное изменение инвентаря.
- **API и UI:** неавторизованный запрос, некорректные данные, серверная ошибка, пустое состояние, отсутствие ложного сообщения об успешном сохранении.
- **БД:** неизвестные ID, отсутствующая запись, нулевое и положительное количество, повторные операции и изолированность тестовых данных.

## Отчёт после задачи

Указывайте: изменённые файлы, выполненные проверки и их реальные результаты, предупреждения, непроверенные сценарии, ветку и SHA коммита. Не заявляйте об успешном деплое или тестах без подтверждения.
