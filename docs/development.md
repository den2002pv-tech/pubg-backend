# Разработка и проверки

## Требования и зависимости

Проект использует Python и FastAPI. Основные зависимости перечислены в `requirements.txt`; `requirements-dev.txt` включает основной список и добавляет pytest.

GitHub Actions настроены так:
- `.github/workflows/tests.yml`: Python 3.12, компиляция `main.py database.py scanner.py tests`, затем `python -m pytest -q`.
- `.github/workflows/counter-tests.yml`: Python 3.11, компиляция `main.py scanner.py tests`, затем `python -m pytest -v tests`.

## Локальная настройка

Пример для Linux/macOS:

```sh
python -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements-dev.txt
```

Для Windows используйте команду активации виртуального окружения для вашего терминала.

Для запуска приложения требуется `DATABASE_URL`, указывающий на PostgreSQL. Не вставляйте строку подключения в исходники, тесты, shell-скрипты или логи. Используйте отдельную локальную тестовую БД и не направляйте тесты на production.

Локальный запуск приложения:

```sh
python3 -m uvicorn main:app --host 127.0.0.1 --port 8000
```

Приложение при старте инициализирует схему БД и синхронизирует каталог карточек, поэтому не запускайте его с неизвестной или рабочей БД. Кроме `DATABASE_URL`, для отдельных сценариев могут понадобиться `TELEGRAM_BOT_TOKEN`, `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET` и другие переменные. Получите полный список поиском по `os.getenv(...)` в коде; не копируйте секретные значения в документацию.

## Проверки

Полный набор тестов:

```sh
python -m pytest -q
```

Тесты каталога `tests`:

```sh
python -m pytest -v tests
```

Компиляция Python-файлов, используемая основным workflow:

```sh
python -m compileall -q main.py database.py scanner.py tests
```

Тесты используют как pytest-функции, так и тесты в стиле `unittest`; pytest запускает оба вида. Успешный статус одного workflow не доказывает, что второй workflow прошёл. Проверяйте фактический результат для SHA конкретного коммита.

## Состояния сканирования и сохранение

`POST /scan` обрабатывает изображение в рамках одного HTTP-запроса и не отправляет промежуточные этапы распознавания. Интерфейс показывает подготовку, фактический прогресс передачи (если браузер сообщает его), ожидание результата и отдельное сообщение при долгом ожидании; внутренние этапы распознавания не выдаются за подтверждённые.

После проверки результатов `POST /me/collection/confirm` атомарно сохраняет выбранные абсолютные количества и возвращает коллекцию, прочитанную из БД. Успешное сообщение показывается только после ответа с подтверждённым числом карт и сохранёнными количествами. Повтор такого запроса безопасен: те же значения обновляют существующие записи, а не добавляются как новые экземпляры. При тайм-ауте подтверждение могло потеряться уже после записи, поэтому интерфейс сохраняет выбранные данные и предлагает безопасный повтор.

## Регрессионные тесты сканирования

Сканер требует двух независимых уровней проверки:

1. **Счётчик на кропе:** `tests/fixtures/counter/cases.json`, изображения в `tests/fixtures/counter/images/`, тесты `test_counter_fixtures.py` и `test_counter_glyphs.py`.
2. **Обнаружение карточек на полном скриншоте:** `tests/fixtures/screenshots/cases.json`, оригинальные изображения в `tests/fixtures/screenshots/images/` и `tests/test_screenshot_fixtures.py`.

Подробные требования к формату разметки, IoU, добавлению случаев, серым и затемнённым картам описаны в [руководстве по регрессионному тестированию скриншотов](scanning-regression.md).

Ключевые правила:
- Эталонное количество и координаты должны быть вручную проверены по оригинальному изображению.
- Не меняйте `expected_quantity` или прямоугольники только ради прохождения теста.
- Сохраните исходные размеры скриншота: координаты относятся к оригиналу.
- Наличие тестов счётчика не доказывает точность обнаружения контуров.
- Если манифест screenshot fixtures пуст, тест размеченных случаев пропускается. На момент последней проверки `tests/fixtures/screenshots/cases.json` содержал пустой список `cases`.
- Поле `state: "unowned"` в текущем тесте не проверяется отдельно по каждой области. Это ограничение документировано; не считайте классификацию владения покрытой до появления явного теста.

Рекомендуемые команды:

```sh
python -m pytest -q tests/test_counter_fixtures.py
python -m pytest -q tests/test_screenshot_fixtures.py
python -m pytest -v tests
```

## Ручной запуск регрессионных тестов счётчика в админке

Открой админку и выбери вкладку «Тесты счётчика». Кнопка «Запустить все тесты» вызывает защищённый административный endpoint `POST /admin/counter-tests/run`, который запускает текущий `scanner._detect_counter` на каждом изображении из `tests/fixtures/counter/cases.json` рабочей ветки `COUNTER_TEST_BRANCH` (по умолчанию `feature/card-counter`).

Результат показывает число пройденных и ошибочных случаев, эталонное и распознанное количества, уверенность, длительность, ошибку загрузки/распознавания и диагностические данные. Можно отфильтровать успешные или ошибочные случаи. Для защиты от устаревшего деплоя локальный кроп используется только при совпадении SHA-256 с манифестом; иначе изображение читается из выбранной ветки GitHub.

Запуск только читает эталоны и изображения: он не меняет `cases.json`, не создаёт Git-коммит, не изменяет каталог карт, инвентарь или пользовательские метрики. Результаты отображаются в текущей сессии админки и не сохраняются в БД. Endpoint требует действующую административную авторизацию и настроенный `GITHUB_TOKEN` с правом чтения репозитория. Отсутствующие или повреждённые изображения отображаются как отдельные ошибки тестов.

## Управление сохранёнными эталонами из админки

Во вкладке «Тесты счётчика» список показывает сохранённые кропы, эталонное количество, количество, зафиксированное при сохранении, и результат сравнения. Меню `⋯` у каждого случая позволяет изменить эталон или удалить случай.

- **Изменить эталон:** допустимое значение — от 1 до 999. Сохраняется поле `expected_quantity`; поле `correct` обновляется сравнением с уже сохранённым `detected_quantity`. Это не запускает детектор повторно и не заменяет значение, полученное текущим алгоритмом. Для оценки текущего алгоритма запустите регрессионный тест.
- **Удалить случай:** удаляет запись из `tests/fixtures/counter/cases.json` и связанное изображение из GitHub, если его путь соответствует каталогу фикстур. Операция создаёт Git-коммит; перед подтверждением убедитесь, что случай действительно ошибочный или больше не нужен.
- **Хранилище:** эталоны и изображения находятся в Git-ветке `COUNTER_TEST_BRANCH` (по умолчанию `feature/card-counter`). Список и изображения загружаются с GitHub; временные превью runtime не являются источником сохранённых эталонов.
- **Ошибки сохранения:** успешное изменение должно вернуть успешный ответ и SHA коммита. При ошибке API интерфейс не должен показывать успешное сохранение. Если коммит не появился в ожидаемой ветке, проверьте `GITHUB_TOKEN`, `GITHUB_REPO`, `COUNTER_TEST_BRANCH` и журнал приложения.
- **Проверка после редактирования:** запустите `python -m pytest -q tests/test_counter_fixtures.py` или кнопку запуска тестов в админке. Ручная коррекция эталона должна основываться на изображении, а не на желаемом результате теста.

При пакетном добавлении сохраняются последние 500 записей манифеста. Старые изображения, вытесненные из манифеста, в текущей реализации не очищаются автоматически и могут остаться неиспользуемыми файлами в Git.

## Git и безопасные изменения

1. Перед работой проверьте фактическую ветку, HEAD и незакоммиченные изменения в локальном Git-окружении. Если доступен только GitHub API, сообщите, что локальный статус не проверен.
2. Рабочая ветка по текущим инструкциям — `feature/card-counter`; не делайте прямых изменений в `main`.
3. До коммита проверьте список файлов и diff.
4. Не включайте временные изображения, логи, секреты и несвязанные изменения.
5. Перед изменением схемы найдите все чтения/записи, ограничения и индексы. Удаляйте данные только после подтверждения, что они тестовые.
6. После отправки изменений проверьте SHA коммита, GitHub Actions и статус деплоя, если эти данные доступны.

## Регрессионные сценарии

- **Инвентарь:** добавление карты, изменение количества, повторное сканирование, нулевые/положительные количества, отсутствие отрицательных значений и согласованность со списком «Ищу».
- **Обмены:** оба участника, право отправить код, повторная отправка, завершение без кода, двойное подтверждение, атомарное изменение инвентаря.
- **API/UI:** запрос без авторизации, некорректные данные, серверная ошибка, пустое состояние, отсутствие ложного сообщения об успешном сохранении.
- **БД:** неизвестные ID, отсутствующая запись, повторные операции и изолированность тестовых данных.

## Отчёт после задачи

Указывайте изменённые файлы, реально выполненные проверки и их результаты, предупреждения, непроверенные сценарии, ветку и SHA коммита. Не заявляйте об успешном тестировании или деплое без подтверждения.

## Проверка встроенного JavaScript в HTML

В обоих CI workflow перед Python-проверками выполняется:

```sh
node scripts/check_inline_js.cjs
```

Скрипт обходит HTML-файлы репозитория, находит встроенные классические блоки `<script>` и компилирует каждый блок без выполнения. Это позволяет поймать синтаксические ошибки, из-за которых браузер может отключить обработчики интерфейса, например вход в админку. В частности, проверка должна обнаруживать буквальные символы `\n`, случайно попавшие в JavaScript вместо реального переноса строки, если они делают блок синтаксически некорректным.

- `.github/workflows/tests.yml` запускает проверку с Node.js 22 перед Python 3.12 и полным pytest.
- `.github/workflows/counter-tests.yml` запускает ту же проверку с Node.js 22 перед тестами на Python 3.11.
- Проверка компилирует встроенный JavaScript, но **не исполняет его в браузере** и не проверяет работу DOM, запросов API, авторизации или взаимодействия пользователя.
- Внешние скрипты, подключённые через `src`, и модульные скрипты пропускаются этой проверкой. Для них нужны отдельные проверки.
- Успешный CI — не подтверждение успешного входа в админку. Критические пользовательские сценарии следует дополнительно покрывать браузерными тестами.

При ручной проверке JavaScript не ограничивайтесь просмотром кода: запускайте синтаксическую проверку и смотрите результат CI для конкретного SHA коммита.
