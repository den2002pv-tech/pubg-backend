## ЭТАП 4. Измерение CPU

Предпочтительно использовать `psutil`, если зависимость уже используется либо её добавление оправдано.

Не добавлять тяжёлые зависимости.

### Для теста и кейсов собирать

Если данные доступны:

- cpu_percent_before
- cpu_percent_after
- cpu_avg
- cpu_peak
- cpu_time_before
- cpu_time_after
- user_cpu_delta
- system_cpu_delta
- observation_duration
- available_cpu_count
- cpu_limit
- metric_source

### Разделять

Отдельно хранить:

- CPU процесса Python;
- CPU контейнера;
- CPU системы.

Не смешивать эти показатели.

### Важно

Если библиотека показывает значения `>100%` для многопоточной нагрузки, сохранить исходную семантику.

### Для теста и кейсов сохранять

- rss_before
- rss_after
- rss_delta
- peak_rss
- vms_before
- vms_after
- process_memory
- container_memory
- memory_limit

### Ограничения

## ЭТАП 6. Мониторинг

Использовать один общий монитор ресурсов.

Монитор должен:

- запускаться перед тестом;
- останавливаться после теста;
- останавливаться при исключениях;
- не накапливать бесконечные массивы;
- не порождать лишние процессы.

### Интервал мониторинга

Предпочтительно `50-100ms`, если это не создаёт заметную нагрузку.

### Важно

Не утверждать, что пик CPU или памяти для короткого этапа измерен точно, если мониторинг интервальный.

Ограничения измерений должны отражаться в отчёте.

## ЭТАП 7. JSON REPORT

После выполнения теста сформировать полный JSON-отчёт.

Предпочтительная структура:

```json
{
  "schema_version": 1,
  "metadata": {},
  "environment": {},
  "summary": {},
  "resource_usage": {},
  "aggregate_timings": {},
  "aggregate_resources": {},
  "cases": []
}
```

Структуру допускается расширять. Смысл разделов должен сохраняться.

### metadata

Содержит:

- start_time
- end_time
- duration_ms
- run_id
- schema_version
- case_count
- processed_count
- passed_count
- failed_count
- error_count
- profiling_mode

Использовать ISO 8601 для времени.

### environment

Содержит:

- python_version
- pillow_version
- psutil_version
- os
- platform
- git_sha
- cpu_count
- cpu_limit
- memory_limit
- container_info

### Категорически запрещено включать

- токены;
- секреты;
- DATABASE_URL;
- ENV с чувствительными данными;
- пароли;
- ключи API.

### summary

Содержит:

- total_cases
- successful_cases
- failed_cases
- passed_quality_checks
- failed_quality_checks
- total_duration_ms
- total_scan_time_ms
- avg_scan_time_ms
- median_scan_time_ms
- max_case_duration_ms
- peak_rss
- peak_cpu

### resource_usage

Содержит:

- start_state
- end_state
- rss
- vms
- peak_rss
- cpu_metrics
- container_metrics
- monitoring_interval_ms
- limitations
- collection_errors

### aggregate_timings

Для доступных числовых метрик рассчитывать:

- count
- sum
- avg
- median
- min
- max
- p90
- p95

где это имеет смысл.

### aggregate_resources

Для каждой ресурсной метрики:

- count
- avg
- median
- min
- max
- p90

Не суммировать показатели, для которых суммирование бессмысленно.

### cases

Для каждого эталона сохранять:

- case_id
- image_path
- image_dimensions
- expected_cards
- detected_cards
- quality_result
- matches
- mismatches
- profile
- timings
- cpu_metrics
- memory_metrics
- status
- error
- measurement_limitations

### Запрещено

Не включать:

- изображения;
- base64;
- содержимое изображений.

Только пути и метаданные.

### Если не удалось загрузить манифест

Не создавать ложный успешный отчёт.

Вернуть понятную ошибку.
