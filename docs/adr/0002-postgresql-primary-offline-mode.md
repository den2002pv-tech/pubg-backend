# ADR-0002: PostgreSQL Primary с локальным SQLite и ограниченным автономным режимом

- **Статус:** предложено к обсуждению; архитектурная готовность не подтверждена
- **Дата:** 2026-11-09
- **Связанный документ:** [ADR-0001](0001-sqlite-authoritative-outbox.md) остаётся историческим документом о варианте B и этим ADR не изменяется
- **Область:** runtime-данные PUBG Mobile Card Collection

## Контекст и цель

Нужно сохранить PostgreSQL в США единственным источником подтверждённых бизнес-данных и продолжить часть пользовательских действий при потере связи с PostgreSQL. SQLite на Enzonic — локальная проекция и, во время недоступности PG, хранилище автономных команд с их локальным статусом. PostgreSQL и SQLite нельзя считать одной транзакционной системой: при нормальной работе PostgreSQL-изменение вместе с Outbox атомарны в PG, а доставка в SQLite происходит позже отдельной транзакцией. Автономная локальная команда также не становится подтверждённой бизнес-операцией лишь оттого, что SQLite её сохранила.

Цель решения — не обещать офлайн-подтверждение там, где приложение не может проверить актуальные данные, а определить узкий набор безопасно откладываемых команд, показывать их как ожидающие подтверждения и после восстановления либо применять через условную проверку PostgreSQL, либо переводить в конфликт для разрешения. Для завершения обмена, которое меняет инвентари двух разных пользователей, автономное принятие запрещено.

## Решение и границы подтверждения

Выбрать вариант A:

1. PostgreSQL — единственная база, в которой операция получает статус **подтверждена**.
2. Для каждой подтверждаемой PostgreSQL-записи бизнес-изменение и событие Transactional Outbox коммитятся одной PG-транзакцией.
3. Outbox consumer переносит уже подтверждённое состояние в SQLite как локальную проекцию, сохраняя порядок и атомарные группы транзакций.
4. Если PG недоступна, SQLite хранит только локальные **автономные намерения** (outbound command journal) и локальный inbox для входящих событий. UI/API явно сообщает `pending_sync` / «ожидает проверки сервером». Это не подтверждённая запись и не должно отображаться как состояние, принятое другим пользователем.
5. После восстановления каждый автономный intent повторно авторизуется и валидируется против текущих PostgreSQL-данных, версии агрегата и бизнес-правил. Он применяется только при выполнении предусловий; конфликт не перезаписывается автоматически.
6. Нельзя одновременно переключать write authority на SQLite и продолжать PG-записи. При неопределённости о доступности PG действует circuit breaker: запрос не запускает независимую попытку записи во вторую БД после неизвестного результата первой.

«Автономная работа» поэтому означает **сохранение некоторых команд локально до подтверждения**, а не глобальное подтверждение операций без PostgreSQL. Если продукт требует немедленного, видимого другим пользователям подтверждения всех операций без связи с PG, вариант A этого не обеспечивает.

### Наблюдаемые проблемы

- `database.py:get_connection()` выбирает PG или SQLite по глобальному `DatabaseManager.mode`; при сбое приложение переключается на SQLite. Это смена write authority, а не режим локального pending journal.
- `_record_outbox()` в `database.py` — заглушка для обычных PG-записей. SQLite row-change triggers пишут события лишь когда функция `database_outbox_enabled()` включена. Обычный PG write и локальная shadow-запись разнесены по разным транзакциям.
- Пользователь и карточки, количества, список «Ищу», очистка коллекции и добавление нулевых карт имеют отдельные PG, SQLite и shadow implementations. В PG ветке сначала идёт commit, затем отдельное обновление SQLite; ошибка копии может поднять ошибку HTTP после успешного подтверждения PostgreSQL.
- `sync_cards()` обновляет и может удалять карточки в PG, а затем отдельно синхронизирует SQLite; этот каталог тоже нужно включить в явный ownership/version contract.
- Админские обработчики `main.py` сохраняют каталог в `card_hashes.json` и файлы `static/cards/*.webp`; PG-таблица `cards` обновляется при startup через `sync_cards(load_db())`. Это ещё один источник записи/порядок распространения, не связанный сейчас с пользовательским Transactional Outbox. Нужно решить, является ли JSON-каталог authoritative для админского редактирования или его изменения сначала фиксируются транзакционно в PG, а assets обрабатываются отдельным durable workflow.
- `/me/collection/confirm` вызывает `get_or_create_user()`, затем `set_user_card_quantities()` и затем повторное чтение коллекции отдельными DB-вызовами. Скан-события и diagnostics записываются отдельно. API-level сохранение коллекции сейчас не является одной транзакцией вместе с созданием пользователя и сохранением коллекции.
- `/me/activity` использует upsert профиля и отметок активности. Частые heartbeat writes создают запись в `users`; это нужно отделить от бизнес-операций (coalesce/TTL или явная репликация) и не создавать из них неограниченную offline очередь.
- `trade_requests.py` создаёт и изменяет заявки в `get_connection()`, затем `_mirror_trade_state_pg_to_sqlite()` отдельно перечитывает заявку и затронутые инвентари из PG и записывает их в SQLite. Это не атомарная доставка Outbox.
- `processed_telegram_updates` пишется отдельной операцией до обработки webhook сообщения; авария после отметки, но до действия, может потерять обработку. Shadow-запись в SQLite опять выполняется отдельно.
- `analytics.py` вставляет события в PG и затем отдельным вызовом зеркалит SQLite. Очистка профилей/таймингов аналитики тоже обновляет две БД отдельно.
- Инициализация `initial_sync_pg_to_sqlite()` сливает таблицы по отдельным выборкам без общего snapshot watermark и может мягко merge-ить локальные/удалённые строки. Это не безопасная начальная репликация для конкурентных записей.
- `db_sync.py` умеет replay локальных row-image и typed operations в PG, группирует по `transaction_id`, ведёт PG markers, но PG primary путь не создаёт соответствующие durable Outbox events; локальная очередь и PG Outbox пока не образуют одну согласованную архитектуру.
- `setup_sqlite_functions()` фиксирует `database_transaction_id()` при настройке соединения. SQLite connection context настраивает функцию один раз, хотя адаптер и callers допускают ручные `commit()` и несколько транзакций в рамках соединения. Поэтому разные транзакции могут получить одинаковый `transaction_id`, в то время как `db_sync.py` группирует pending events по этому полю. Идентификатор транзакции должен привязываться к фактической DB-транзакции, а не к соединению.
- `OutboxManager.add_operation()` пишет отдельным SQLite connection/transaction. Если helper вызвать после бизнес-изменения, между ними нет атомарности. SQLite triggers дают другой путь capture, но сейчас они условно включаются режимом и не создают Transactional Outbox для PG write path.
- Используются PG-специфичные выражения (`ILIKE`, `FILTER`, `ANY`, `unnest`, `::jsonb`, `INTERVAL`, `RETURNING`, `FOR UPDATE`, `setval`) и адаптер SQL для SQLite. Это усложняет безопасное переключение и затрудняет доказательство эквивалентных условий.

## Схема взаимодействия

```text
Обычная доступность PostgreSQL

Клиент/API
   │ команда + idempotency_key + expected_version
   ▼
PostgreSQL: BEGIN
   ├─ проверка auth, версии и бизнес-предусловий
   ├─ изменение бизнес-таблиц
   ├─ INSERT в outbox_events / outbox_transactions
   └─ COMMIT ───────────────► API отвечает «подтверждено»
                                  │
                                  ▼
                         Outbox dispatcher/consumer
                                  │ at-least-once
                                  ▼
                         SQLite transaction:
                         применить целую PG-транзакцию,
                         marker + watermark, COMMIT

PostgreSQL недоступна

Клиент/API ─► SQLite: BEGIN IMMEDIATE
              ├─ сохранить command с базовой версией, scope,
              │  idempotency_key и локальным порядком
              ├─ при разрешённом типе обновить локальную
              │  pending-проекцию или draft state
              └─ COMMIT ─► API отвечает «сохранено локально,
                            ждёт проверки сервером»

Восстановление PG ─► сверить версии ─► применить/конфликт/отклонить
```

SQLite-проекция содержит данные PG на watermark `pg_outbox_cursor` плюс отдельно маркированные локальные intents. UI не должен маскировать незавершённую команду под подтверждённое состояние. Если для отрисовки показывается optimistic state, рядом видны статус pending/conflict и последнее время синхронизации.

## Transactional Outbox для подтверждённых операций

Для обычной PG-записи единый repository/service метод выполняет одну транзакцию:

```text
BEGIN (PostgreSQL)
  проверить ключ операции и вернуть прежний результат при повторе
  проверить права, aggregate_version и доменные предусловия
  изменить все связанные строки
  повысить версию затронутого агрегата/агрегатов
  записать outbox transaction envelope и упорядоченные события
COMMIT
ответить успехом только после commit
```

Рекомендуемая модель Outbox:

- `transaction_id` — UUID одной бизнес-транзакции;
- `event_id` — глобально уникальный UUID каждого события;
- `event_sequence` — порядок событий внутри транзакции;
- `aggregate_type`, `aggregate_id`, `aggregate_version`;
- `event_type`, `schema_version`, `payload`, `created_at`;
- для операций с несколькими агрегатами — единый envelope с полным набором событий и общей транзакционной границей;
- отдельная таблица `processed_idempotency_keys` с уникальным `(client_scope, idempotency_key)` и сохранённым итоговым ответом.

Consumer применяет группу событий SQLite-транзакцией: проверяет, что все expected aggregate versions совпадают; обновляет все записи/удаления, marker `applied_transaction_id` и per-aggregate versions; фиксирует commit. Падение до commit оставляет группу неприменённой. Падение после commit до подтверждения consumer приводит к повторной доставке, которую marker превращает в no-op. События одной PG-транзакции не разделяются между SQLite commits. Доставка at-least-once, эффект идемпотентен.

Текущий список данных-кандидатов для репликации требует окончательной инвентаризации: `users`, `cards`, `user_cards`, `desired_cards`, `trades`, `trade_requests`, `processed_telegram_updates`, `user_analytics_events`. Для каждой таблицы фиксируются owner, PK, FK, delete semantics, версия, PII/retention и порядок репликации. Локальные locks, cursor и command journal в PG не реплицируются. Иконки и Git-managed fixtures остаются внешними ресурсами с отдельными потоками.

Удаления передаются явными delete/tombstone событиями. Нельзя периодически сравнивать полные таблицы и безусловно перезаписывать SQLite: такой snapshot допустим только для bootstrap с остановленными writes или для создания новой snapshot-версии с точным watermark.

## Локальная реплика и восстановление SQLite

- Consumer получает только зафиксированные Outbox envelopes. Не считать `BIGSERIAL` или timestamp глобальным commit order: sequence может выделиться до commit, поэтому consumer может увидеть больший номер, пока транзакция с меньшим ещё не видна. Использовать per-aggregate `previous_version → new_version` условия и не продвигать локальную версию через gap. Событие для нескольких агрегатов ждёт совпадения всех previous versions и применяется целиком. Для snapshot bootstrap нужен согласованный snapshot с WAL/LSN границей или другой доказуемый fence.
- Данные транзакции применяются атомарно, FK включены, JSON и UTC timestamp нормализованы.
- На старте проверяются SQLite integrity, schema version, последний cursor и целостность pending command journal. Проверка наличия таблиц не доказывает, что snapshot актуален.
- При пропуске/повреждении cursor consumer ставит локальную реплику в `stale/rebuild_required`; приложение не читает из неё как из актуального fallback, пока не завершит snapshot с watermark и replay событий после него.
- Bootstrap выполняется согласованным PostgreSQL snapshot с логической границей (consistent snapshot + соответствующий Outbox position/LSN или эквивалентный протокол). Все таблицы копируются в staging SQLite; счетчики строк, FK и контрольные суммы сверяются до атомарной замены файла/активации. Обновления, произошедшие после snapshot, воспроизводятся по Outbox.
- SQLite WAL/checkpoint и резервное копирование должны учитывать `-wal`/`-shm`: нельзя копировать только основной файл во время активных записей. Нужен SQLite backup API или остановленный/checkpointed backup, затем регулярная проверка restore.

## Автономный режим и политика по операциям

Автономная запись означает, что SQLite долговечно сохранила **команду для последующей проверки**, а не что бизнес-операция уже подтверждена PostgreSQL. Все команды имеют `command_id`, `idempotency_key`, пользователя/tenant, исходную aggregate version, fingerprint исходных данных, время локального создания, client/app version, статус и результат reconciliation. Payload минимизируется; секреты и Telegram exchange codes не кладутся в общий журнал.

| Операция | Можно записать локально при outage? | Предварительные проверки на локальном snapshot | Что происходит при восстановлении PG | Политика интерфейса |
| --- | --- | --- | --- | --- |
| Изменить количество одной карты абсолютным значением | Да, как provisional intent; локально применять только в optimistic overlay | Auth Telegram уже проверена, карта есть в snapshot, диапазон 0–999, baseline version/value известны | Применить условный `set quantity` только если версия пары `(user, card)` или inventory aggregate совпадает с baseline. Иначе conflict; не использовать last-write-wins. Повтор с тем же key возвращает исходный результат | «Сохранено на устройстве, ждёт сервер»; после конфликта предложить загрузить серверное значение и повторить выбор |
| Сохранить коллекцию после сканирования | Да, как одну batch-команду; не создавать подтверждённое состояние PG | Проверить формат, дубликаты ID, границы количества, принадлежность карточек локальному каталогу; сохранить `save_id`, baseline inventory version и точный список затронутых карт | Атомарно применить всю batch-команду, если aggregate version совпадает. При изменении хотя бы затронутой части отклонить batch как конфликт; не применять частично и не считать повторный scan безусловно идемпотентным, если это не тот же `save_id` | Pending статус для всего сохранения; конфликт требует явного повторного просмотра |
| Задать список «Ищу» | Да, как provisional intent | Локально проверить уникальность ID, известность карт и собственный snapshot; сохранить baseline wishlist/inventory version | CAS по версии списка и проверка текущего инвентаря. Если карта уже появилась в инвентаре — серверное правило исключает её либо возвращает конфликт; повторный список с тем же key идемпотентен | Список помечен pending; не показывать другим пользователям до PG commit |
| Добавить нулевые карты в инвентарь | Да, как provisional monotonic add, если каталог известен | Дедупликация card IDs, лимит batch, существование в версии локального каталога | Условное `INSERT ... ON CONFLICT DO NOTHING` после сверки активного каталога; безопасный повтор не меняет положительные количества | Pending; локально показывать как нулевые provisional записи |
| Очистить коллекцию | Можно сохранить intent, но по умолчанию не применять optimistic mass-change; отдельное подтверждение пользователем | Зафиксировать baseline версии всей коллекции и полный scope удаления | Только CAS всей коллекции. При любой изменившейся версии конфликтует целиком; никогда не повторять безусловно поверх новых PG данных | Сообщить, что запрос ждёт сервер; после конфликта запросить повторное подтверждение |
| Создать заявку на обмен | Можно записать черновик/команду на submit, но нельзя создать видимую действующую заявку или слать уведомление | Проверить локально ID, карточки и snapshot наличия дубликата/спроса; это лишь предварительная проверка | Сервер заново проверяет взаимный match, количества и wishlist. При успехе создаёт заявку в PG и notification outbox; при изменении данных возвращает отказ/конфликт | «Черновик ожидает отправки»; получатель не видит и не принимает до PG commit |
| Принять, отклонить, отменить заявку / согласиться на обмен | Команду можно локально записать как pending intent; смена состояния не считается принятой | Проверить actor и локальный status/version, но явно пометить как устаревающий snapshot | Перепроверить роль, переход, текущий status/version и допустимые предшествующие состояния. Конкурирующий или устаревший переход — conflict/no-op по исходу, без перезаписи | Не отправлять участникам подтверждение до PG commit |
| Ввести/передать код обмена | Нет для хранения/доставки во внешний канал; при необходимости клиент может безопасно оставить ввод у себя до восстановления | Код чувствителен; локальный persistent journal избегать | После reconnect повторно авторизовать и отправить напрямую в серверный flow; не считать повтор доставленным без серверного receipt | Требовать повторной отправки; не логировать код |
| Завершить обмен и передать карточки двум пользователям | **Нет. Запрещено в автономном режиме** | Snapshot не может гарантировать, что стороны/другие операции не изменили инвентари и заявку | Только одна транзакция PostgreSQL с lock заявки, проверкой обеих сторон и обеих количеств, изменением обоих инвентарей, wishlist-правил, completion state, версии и Outbox envelope | Кнопка/endpoint завершения недоступны или отвечает 503 с сохранением чернового пользовательского контекста; после reconnect пользователь повторяет действие |
| Telegram webhook update | Сохранить update в local inbox можно; выполнять бизнес-эффект можно только через автономные command policies выше | Уникальный `update_id`; сохранять minimal payload/тип и статус `received`, не маркировать `processed` раньше durable capture; локальная dedupe | Для допустимого события создать/переиспользовать idempotent command и обрабатывать с новым серверным auth/context. Недопустимое действие остаётся deferred/rejected. Обработать событие и записать dedupe marker одной PG-транзакцией | Telegram получает быстрый 2xx после durable inbox capture; пользовательские подтверждения/уведомления только после серверного решения |
| Аналитика / scanner diagnostics | Да; best-effort queue с ограничением размера/срока | Санитизация, лимиты payload, удаление PII/секретов, sampling | Отправка с event UUID, unique PG constraint, `ON CONFLICT DO NOTHING`; при истечении retention можно отбросить telemetry по документированной политике | Не блокировать основное сохранение из-за аналитики; явно ограничить очередь и метрики потерь |
| Обновление каталога, админская запись, удаление карты | По умолчанию нет; только command draft с админ-правом и ревизией каталога | Проверить локально роль невозможно, если сессия/ACL stale; каталог может быть изменён параллельно | Подтверждать только в PG с серверной авторизацией и условием catalog version; затем реплицировать | Админские destructive changes требуют PG; offline запрет |

Локальная проверка auth не продлевает истёкшую сессию без ограничений. Для автономной команды нужны короткий срок годности, проверенный Telegram initData/токен, привязка к actor и защита от повторного применения. Если сервер не может безопасно подтвердить личность, команда остаётся на клиенте и не попадает в journal.

### Конфликты и reconciliation

- Каждая бизнес-строка/агрегат получает `version` (монотонный integer) или сравнимый server revision. Локальная команда указывает точный baseline. Обычные timestamp не являются версией.
- Изменение строки/агрегата в PG после baseline означает конфликт для non-commutative команд. Никакого автоматического last-write-wins, upsert-перетирания или merge множеств для коллекции/wishlist.
- При conflict сохраняется локальный intent для показа пользователю, но он не накладывается поверх текущего PG state и не блокирует новые подтверждённые PG-записи. Разрешение — повторно отредактировать команду на свежих данных с новым `idempotency_key` и новым baseline.
- Разрешённые commutative операции могут применяться повторно только если для данного типа математически доказана коммутативность, не нарушаются ограничения количества и она не взаимодействует с trade transitions. В текущих API преимущественно передаются абсолютные значения, поэтому общее правило — конфликтовать при несовпадении версии.
- Reconciliation каждого intent атомарна в PG: dedupe key, проверки, доменное изменение, результат команды, Outbox событие. Статус локального journal меняется в отдельной SQLite-транзакции после получения результата. Если ответ PG потерян после commit, повтор вернёт результат по idempotency key.
- Нельзя объявлять intent разрешённым только по локальному receipt. PG сохраняет детерминированные `applied/rejected/conflict` result и digest входной команды.

## Обмен карточками и отсутствие двойного подтверждения

Обмен затрагивает как минимум заявку, инвентарь отправителя и инвентарь получателя; иногда также обе wishlist записи и уведомления. Он не может безопасно завершиться через две локальные SQLite базы/неактуальные снимки.

В PG одна транзакция завершения обязана:

1. Захватить trade row `FOR UPDATE` и проверить ожидаемый status/version.
2. Проверить права обеих сторон, согласия, обменный код/receipt и лимиты повтора.
3. Условно списать нужный экземпляр с каждой стороны с `quantity > required`; проверить количество изменённых строк.
4. Начислить карты другой стороне, обработать «Ищу» по правилам проекта.
5. Перевести заявку в `completed`, повысить версии всех затронутых агрегатов.
6. Записать один Outbox envelope со всеми row changes и notification commands.
7. Commit; только затем ответить обоим участникам об успехе и доставлять уведомления через отдельный notification Outbox.

SQLite не выполняет transfer и не ставит карточки в окончательное состояние при offline. Если пользователь нажал завершить во время outage, сохранить только необязывающее локальное намерение/черновик без статуса completed, иначе отказать с retryable сообщением. При reconnect PG проверяет актуальное состояние с нуля. Telegram callbacks, кнопки в Mini App и webhook используют один idempotency namespace/command service, чтобы одно действие не проходило разными путями дважды.

## Идемпотентность и дубликаты

- API write принимает idempotency key (или стабильный `save_id`/Telegram `update_id`) и включает actor + operation scope; hash нормализованного payload сохраняется в PG с итоговым ответом.
- Повтор того же key и payload возвращает сохранённый outcome. Тот же key с другим payload — 409 и диагностика.
- Telegram update dedupe хранится в PG вместе с эффектом обработчика/созданной командой. Local inbox имеет уникальный `update_id` и состояния `received`, `queued`, `resolved`, `rejected`; повторный webhook не запускает второй effect.
- Outbox transaction/event UUID уникальны. Consumer хранит applied marker вместе с изменениями SQLite. Crash после PG commit и до HTTP response/consumer ack не создаёт дублей.
- Не использовать `ON CONFLICT DO NOTHING` как единственную доменную проверку: уникальный constraint защищает от повтора, но бизнес-ответ и версия результата должны сохраняться.
- Для аналитики допустимы event UUID и retention/loss policy; для инвентаря/обмена нельзя supersede журналом более позднего значения.

## Несколько процессов, Enzonic и ограничения SQLite

При доступном PostgreSQL общие записи могут обслуживаться несколькими web workers. На каждом Enzonic instance local SQLite — отдельная копия с собственным cursor и автономным journal. Локальные автономные intents должны синхронизироваться в общий PG через idempotency/CAS, а не путём синхронизации SQLite-файлов между инстансами.

Во время PG outage независимые локальные журналы создают UX и durability ограничения: следующий запрос пользователя может попасть на другой instance, а потеря instance до reconciliation теряет его provisional commands. Поэтому до поддержки multi-instance offline режима нужен один fenced active offline-acceptor с постоянным volume и маршрутизацией к нему либо протокол повторной отправки command из клиента с тем же key плюс доступный способ просмотреть статус. Распределённые SQLite-файлы нельзя автоматически объединять. Если Enzonic не предоставляет надёжного leader/fencing и хранения, production offline command acceptance следует ограничить одним закреплённым экземпляром; остальные узлы отвечают retryable error во время outage.

SQLite WAL допускает конкурирующие reader-ы и единственного writer одновременно на одном DB-файле, но нельзя выводить из этого, что сеть/том Enzonic обеспечивает нужные locks. При нескольких процессах на одном локальном диске нужны `busy_timeout`, короткие write transactions, retry только для `SQLITE_BUSY`, один consumer lease на файл и crash recovery. При разных хостах локальные SQLite независимы — это нормально как отдельные PG read replicas, но нельзя считать один локальный pending journal общим между ними. Offline intents допустимы только при SQLite-проекции, не старше заданного порога и прошедшей integrity/cursor checks. Это не гарантирует отсутствие неуспевшего дойти PG события, поэтому каждая команда обязана указывать baseline version, которую reconciliation проверяет в PG; version mismatch превращает intent в conflict.

Публичная страница Enzonic описывает два разных пути: Enzonic Deploy запускает API routes как функции, стартующие по запросу и масштабируемые до нуля; отдельный Cloud server hosting описан как постоянный сервер с реальной файловой системой и автоматическими backups data directory. На странице также указаны отдельные servers для app/DB и возможность клонировать server за load balancer. Эти общие заявления **не подтверждают конфигурацию конкретного приложения**, гарантию персистентности его mount, shared path для процессов, crash-consistent SQLite backup, режим WAL, backup retention или восстановление. Ссылки: [Enzonic hosting page](https://enzonic.com/web-hosting), [Enzonic Deploy](https://deploy.enzonic.com/).

До выбора пути в Enzonic panel/support необходимо получить ответы: какой продукт обслуживает `pubg-card.enzonic.dev` (Deploy или Cloud server), фактическое количество live instances/processes и их размещение, диск/volume path и lifetime при redeploy/restart/clone, shared/local semantics, backup schedule/retention/restore, поддержка SQLite WAL locks на mount, гарантия завершённого fsync, маршрутизация и fencing одного active offline-acceptor. ## Сравнение A и B

Оценки качественные; численные claims о скорости, стоимости или throughput без измерений не делаются.

| Критерий | A. PG Primary + SQLite Local Replica и offline queue | B. SQLite Primary + PG Replica |
| --- | --- | --- |
| Нагрузка Enzonic | Каждая онлайн-запись пишет PG; локально consumer пишет replicated rows, cursor и queue. На outage растёт локальный журнал/reconciliation. | Все бизнес-чтения/записи идут в локальный файл; интенсивность WAL, блокировок и backup ложится на Enzonic. |
| Нагрузка PostgreSQL | Основная бизнес-нагрузка плюс Outbox insert/read; при восстановлении snapshot/reconciliation может дать всплеск. | Только асинхронная доставка/репликация и downstream reads; возможен backlog flush после outage. |
| Сетевой трафик | Онлайн-запросы к PG и PG→Enzonic Outbox события; после восстановления Enzonic→PG автономные commands. | Приложение не обязано обращаться в PG на пользовательский запрос; Enzonic→US доставка каждого локального event. |
| Сложность разработки | Высокая: две направленные очереди разных типов (PG event replica и SQLite command reconciliation), версии, conflict UX, partial offline availability. | Высокая: SQLite как authoritative store, single-writer topology, durability/backup и полный event replication на PG. |
| Риск потери данных | PG commit durable; SQLite cache восстанавливается из PG. Подтверждённые офлайн команды до PG commit можно потерять при потере local disk; их нельзя называть подтверждёнными | SQLite commit подтверждает операцию; потеря локального диска до доставки в PG теряет подтверждённые записи. |
| Работа при потере связи с PG | Чтение из последней копии; ограниченные локальные команды остаются provisional и позже конфликтуют или применяются | Полная локальная работа возможна при одном authoritative SQLite и устойчивом volume. |
| Атомарность обменов | Полная при PG online; завершение во время outage запрещено | Может быть атомарным локально, но тогда PG eventual. |
| Восстановление | Перестроить SQLite из консистентного PG snapshot + Outbox; reconcile commands по версиям | Восстановить SQLite из local backup; PG отстаёт на backlog и не гарантирует нулевой RPO при потере volume. |
| Масштабирование | Удобнее для нескольких инстансов благодаря PG; каждой реплике нужна собственная SQLite, а команды координируются через PG | Несколько процессов на одном SQLite file возможно с сериализацией writes; независимые host-local файлы дают split-brain. |
| Сопровождение | Нужно поддерживать возраст/полноту проекции, offline UX, конфликтную очередь и безопасность автономных команд | Нужно сопровождать локальную БД как критическую базу и направленный репликатор. |

Вариант A лучше сохраняет подтверждённое состояние при отказе Enzonic, позволяет восстановить локальную копию из PG и соответствует требованию единственного подтверждающего источника. Цена — offline-действия ограничены условными intent, которые могут быть отклонены. Вариант B поддерживает более широкий offline write surface, но переносит риск подтверждённых операций и single-writer ограничения на Enzonic.

## Восстановление после сбоев

| Точка сбоя | Поведение |
| --- | --- |
| PG transaction rollback до commit | Нет подтверждённого изменения и Outbox; клиент может повторить запрос с тем же key. |
| PG commit прошёл, HTTP ответ потерян | Повтор по idempotency key возвращает сохранённый результат. |
| PG commit прошёл, SQLite consumer не запустился/упал | Event остаётся в PG Outbox; consumer применит позже. PG остаётся authoritative. |
| SQLite применил событие, но consumer не успел ack | Повторная доставка упирается в local applied marker; дубликата нет. |
| PG потеряна до начала запроса | Для разрешённого типа SQLite сохраняет pending intent; для запрещённого — API возвращает retryable error без ложного success. |
| PG commit outcome неизвестен из-за разрыва | Не переключаться сразу на локальное исполнение того же write; сначала проверить operation key в PG при восстановлении. Иначе одна операция может попасть в обе базы с разными исходами. |
| Enzonic restart при локальном pending intent | После восстановления из durable volume consumer сохраняет journal; повторно валидирует в PG. Если volume отсутствует/повреждён — команда считается потерянной, это показывается как ограничение RPO. |
| SQLite повреждена или cursor непоследователен | Не использовать stale projection для решения trade/match; создать новый snapshot, затем replay. Pending intents архивировать/сверить отдельно, не удалять молча. |
| PG восстановилась, но intent конфликтует | Перевести в `conflict`, сохранить локальную копию для пользователя, не менять PG и не повторять бесконечно. |
| SQLite/PG диск заполнен | Не подтверждать локальную запись/репликацию без durable commit; сигнализировать состояние и ограничить/сэмплировать только необязательную аналитику по отдельной политике. |

В online write path при сетевом timeout нельзя определить по одному клиентскому исключению, успел ли PG commit. Повторная попытка должна всегда использовать тот же idempotency key. Автоматический failover в SQLite допустим только после классификации отказа и только в очередь локальных pending commands, но никогда не как повторная запись «считать уже подтверждённой».

## Миграция текущих данных и переход

Текущие данные PG остаются первичными. Безопасный bootstrap выполняется с maintenance/read-only окна или с доказуемым snapshot + Outbox boundary:

1. Зафиксировать используемый Enzonic продукт, БД, таблицы и фактические writers; определить, какие из существующих изменений в локальной SQLite уже отражены в PG. Не запускать merge вслепую.
2. Сделать проверяемые backups PG и SQLite, зафиксировать row counts, PK диапазоны, контрольные суммы и статусы обменов. Текущая SQLite может содержать только частичную копию и pending/local-only события.
3. Остановить или сериализовать writes на время bootstrap либо внедрить snapshot/Outbox LSN протокол. Установка PG Outbox и cutover чтения делаются без окна потери событий.
4. Создать PG transactional Outbox/operation idempotency tables и версии агрегатов отдельной schema migration. Не переписывать историю приложения и не запускать разрушительный мигратор до проверки на копии.
5. Очистить/создать staging SQLite **только после резервирования и классификации локальных данных**. Загрузить из консистентного PG snapshot все runtime-таблицы в FK порядке; сохранить IDs, состояния, timestamps и JSON, настроить counters.
6. Сверить таблицы и отношения: row counts, PK uniqueness, FK, catalog IDs, инвентари, wishlists, все статусы trade requests, processed webhook IDs и выбранную аналитику. Ошибки и локальные записи, отсутствующие в PG, рассматриваются пооперационно; ни merge по ключу, ни last-write-wins не принимаются автоматически.
7. Включить PG transactional Outbox на все новые writes, начать consumer с точного watermark, сравнить event lag и row hashes. Проверить, что операции после snapshot не пропущены.
8. Переключить reads на PG primary и SQLite read replica. После проверки покрыть только разрешённые команды локальным journal. Удалить DML права у обычных read/consumer ролей по минимальным полномочиям; consumer PG→SQLite читает Outbox, не меняет бизнес-данные PG.
9. Поддерживать rollback window с сохранёнными backups. Если нужно вернуться на предыдущий код, сначала остановить writes и определить все подтверждённые PG-коммиты и локальные pending commands. Нельзя переключиться на старый режим, который слепо пишет в обе базы.

Потеря существующих PG данных предотвращается тем, что PostgreSQL не очищается и не принимает пересоздание/слияние как cutover, пока staging copy не сверена. Локальные SQLite-only changes нельзя считать автоматически корректными: отдельно определить, были ли это ранее выданные пользователю подтверждения, pending операции или просто stale mirror. До завершения этой классификации миграция не безопасна.

## Прямые PG-записи и разделение прав

- Web/API использует общий write service. Чтобы raw DML не мог обойти Outbox, enforce-ить один механизм: (a) отозвать table DML и разрешить только контролируемые stored procedures, которые меняют строки и создают события, либо (b) использовать PG triggers на всех реплицируемых таблицах, которые пишут row-image envelope в той же транзакции и откатывают её при отсутствии валидного transaction context. Только соглашений Python-кода и статического поиска недостаточно, если роль всё ещё может менять таблицы напрямую.
- PG transaction context для triggers устанавливается транзакционно-локальной настройкой в write service и связывает row events одной DB-транзакции. Envelope хранит затронутые aggregate IDs, before/after versions, schema version и idempotency key. Consumer не продвигает глобальный sequence cursor через невидимый/uncommitted gap; либо используется commit-LSN stream, либо агрегатные version gates.
- SQLite replica consumer имеет SELECT на PG Outbox; для SQLite ему нужны write permissions только на файл локального replica. Он не применяет бизнес-DML в PG.
- Offline reconciler имеет отдельный ограниченный PG role или общий repository service; операции проходят те же доменные checks/CAS, audit и Outbox, что обычные online requests.
- Админские endpoints, catalog loader, analytics cleanup, scheduled jobs и webhook не получают путь прямой записи, минующий repository/outbox. Миграции DDL запускаются отдельной deployment role.
- Проверить статическим поиском все `psycopg.connect`, `get_pg_connection`, `get_connection`, прямые SQLite connections и `commit()` callsites; тесты прав должны доказывать запрет обхода согласованного слоя.
- PG read replicas/analytics consumers read-only. Если другой сервис сейчас пишет в те же таблицы, его включить в общий command/repository contract или запретить такую запись.

## План реализации

1. **Полная инвентаризация:** описать все read/write paths, границы транзакций, семантику каждой операции, PG-specific SQL, роли, таблицы и внешние эффекты. Отдельно определить, какие текущие изменения дерева относятся к уже начатой реализации и не потерялись.
2. **Подтвердить deployment topology:** получить от Enzonic фактический тип продукта, диск, процессы/instances, backup и restore гарантии. Выбрать per-instance SQLite или один instance. До подтверждения offline writes оставить выключенными.
3. **Задать контракты:** PG Outbox envelope, aggregate version, idempotency keys, SQLite cursor, local command journal, conflict statuses, retention, limit/backpressure, payload PII policy.
4. **Разработать PG repository/outbox:** атомарные доменные updates и Outbox для всех таблиц, включая admin/catalog, analytics, webhook, trade completion и notification intents. Включить read-your-write и повтор key.
5. **Разработать consumer и snapshot bootstrap:** ordered atomic groups, cursor/lease, retry, dead-letter, gap detection, rebuild из согласованного snapshot; запрет plain merge.
6. **Разработать только допустимый offline command set:** inventory absolute/batch с CAS, wishlist CAS, zero-card additions, drafts заявок, webhook inbox и analytics queue. Сделать `pending/conflict/rejected/applied` явно видимыми в API/UI. Trade completion и чувствительные code-delivery действия оставить online-only.
7. **Закрыть обходные PG/SQLite пути:** централизовать repository calls в `database.py`/новом service layer, убрать зеркалирование и неявное переключение mode. Проверить permissions и прямые коннекты.
8. **Наблюдаемость и runbooks:** outbox lag/oldest age, replica cursor, local snapshot age, pending command count/age, conflict rate, retry/error classes, disk usage, backup age/restore status. Runbooks для outage, rejoin, SQLite rebuild, pending conflict и disk-full.
9. **Репетиция и cutover:** отдельные копии БД, полный reconcile, нагрузка и chaos tests. Затем maintenance cutover, сначала PG Outbox+SQLite replica, и только после проверки включение ограниченных autonomous command types за feature flags.
10. **Постепенный выпуск:** отдельно включать offline количества, collection batch, wishlist, затем заявки как deferred drafts. Completion trade остаётся запрещённым при outage. Каждый флаг имеет kill switch и метрики конфликтов.

## План тестирования

Автотесты должны запускаться на изолированной PG schema и временных SQLite files. Ни один тест не использует production `DATABASE_URL`. Тесты не запускались при подготовке этого документа.

### Атомарность и Outbox

- Принудительная ошибка после доменного DML, но до Outbox insert, и наоборот: PG rollback не оставляет ни бизнес-строку, ни событие.
- PG commit и HTTP response loss: повтор с тем же ключом возвращает один результат/один Outbox envelope.
- Consumer crash до SQLite commit, после commit до ack, повторная доставка, неправильный sequence и неправильный hash.
- Commit/visibility order: транзакция с меньшим выделенным sequence задерживается и коммитится после транзакции с большим sequence; consumer не пропускает её и version-gated apply ждёт предыдущих aggregate versions.
- Multi-row trade transaction остаётся одной группой в PG и одной SQLite transaction; FK/check constraints валидны после применения.

### Outage и конфликтное восстановление

- Connect failure до запроса, statement timeout, connection reset до/после PG commit: offline journal не создаёт двойного эффекта.
- PG row version меняется параллельно с offline absolute quantity, batch collection и wishlist: команда конфликтует полностью, PG и replica state не перетираются.
- Zero-card addition идемпотентно применяет только карточки актуального каталога.
- Draft trade после outage повторно проверяет reciprocal match; получатель не видит заявку до PG commit.
- Любой offline completion trade отклоняется локальной политикой и endpoint/API не показывает completed.
- Повтор Telegram update после падения на каждом шаге inbox→command→PG commit→notification; один бизнес-эффект и управляемая доставка уведомления.
- Analytics queue bounded, sanitize, duplicate event no-op, documented drop on quota/retention.

### Обмен и бизнес-регрессии

- Недостаточное количество у одной стороны, два параллельных completion, повтор callbacks, удалённая/отменённая заявка, повтор кода, изменение wishlist; ни один путь не приводит к частичному списанию/зачислению.
- Успешный online exchange изменяет обе стороны и status в одной PG transaction; SQLite отражает все или ничего.
- После конфликтной pending команды коллекция/«Ищу» пересчитываются из PG; количества 0, положительные количества, повторное сканирование и устойчивые card IDs.

### Bootstrap, эксплуатация и безопасность

- Snapshot при конкурентных PG writes с корректной Outbox boundary, replay без gap, точные row counts/checksums и sequence values.
- Stale/corrupt SQLite, schema mismatch, удалённый cursor gap, WAL recovery, перезапуск процессов и SQLite busy.
- SQLite disk full/read-only, PG длительно недоступна, локальный volume заменён/потерян; проверенные user-facing статусы и RPO.
- Многопроцессный race на одном файле (если этот режим поддерживается) и отдельные локальные файлы на разных инстансах; проверить, что reconciliation не зависит от общей SQLite.
- Permissions: consumer не может делать PG DML; приложение не может писать в обход repository/outbox; offline code не попадает в логи/аналитику.
- Восстановление из PG snapshot плюс Outbox и из backup SQLite проверяется как отдельный runbook с измеренными RTO/RPO.

## Ограничения, риски и решения, которые ещё нужны

1. **Нет полного подтверждения всех путей записи.** Текущий поиск нашёл основные runtime write surfaces в перечисленных модулях, но до реализации нужен AST/SQL audit по всему репозиторию, включая редкие админские endpoints и внешние deployment jobs. Поэтому ADR не объявляет архитектуру готовой.
2. **Автономные intents могут быть отклонены.** Интерфейс должен объяснить это до записи; продукт должен решить срок хранения, UX конфликта и что считать локально сохранённым при потере телефона/Enzonic volume.
3. **Enzonic topology неизвестна.** Нельзя подтвердить mount persistence, процессное/межхостовое sharing, WAL locks, backup consistency или retention для текущего приложения только по репозиторию.
4. **Offline trade ограничен.** Создание может остаться только черновиком; принятие требует повторной проверки; завершение и передача карт требуют PG.
5. **Неизвестный PG commit outcome.** Только idempotency key позволяет безопасно выяснить судьбу операции после восстановления сети; нельзя автоматически исполнять её как новую SQLite mutation.
6. **Нагрузка не измерена.** Outbox, SQLite consumer и replay backlog добавят I/O и сеть. Оценивать по измерениям на фактическом Enzonic объёме и профиле пользователей.
7. **Критичные внешние эффекты.** Telegram notification не входит в PG транзакцию; нужен notification outbox и retry/idempotence, иначе обмен зафиксируется, но уведомление может задержаться или повториться.
8. **Авторизация при outage.** Должны быть короткие и ограниченные правила использования проверенной auth; stale authorization нельзя считать безусловно действительной.
9. **Analytics и персональные данные.** Требуют отдельного retention, consent/privacy и transfer scope; их очередь не должна бесконечно занимать SQLite.
10. **Решения до реализации:** какие данные/UI показывают pending; срок жизни offline command; допустимый конфликт UX; авторитетность `cards` catalog; read fallback при слишком старой SQLite; политика offline profile/activity; хранение и отправка Telegram inbox payload; идемпотентность client `save_id`; RPO/RTO и backup owners.

## Вывод

Вариант A **реализуем** и архитектурно подходит, если «продолжать работу» означает ограниченно сохранять provisional commands и локально читать последнюю SQLite-копию, а PostgreSQL остаётся единственной точкой подтверждения. Полное автономное создание и завершение обмена безопасно не обеспечить без координации с PG. Массовые абсолютные обновления коллекции/списка «Ищу» требуют optimistic concurrency и конфликтного UX.

Нужен существенный рефакторинг существующих DB paths, а не переключение флага `DatabaseManager.mode`: требуется PG transactional Outbox, локальный consumer, отдельный SQLite command journal, idempotency/versioning и явное состояние pending/conflict в API. Включать автономные записи до этого и до проверки Enzonic storage/instance topology небезопасно.
