# ADR-0001: SQLite как источник записи, PostgreSQL как удалённая реплика

- **Статус:** предложено, реализация не начата
- **Дата:** 2026-11-09
- **Область:** runtime-данные приложения PUBG Card Scanner

## Контекст

Текущая схема PostgreSQL + SQLite использует PostgreSQL как обычную основную БД и переключает приложение на SQLite при сбое. Между ними нет общей транзакции. Для ряда операций PostgreSQL фиксируется раньше, чем обновляется SQLite; сбой при shadow-write оставляет локальную копию позади уже подтверждённого состояния. Outbox в SQLite не исправляет это для штатных PostgreSQL-записей, поскольку `_record_outbox()` в `database.py` сейчас является заглушкой. В SQLite-режиме row-change triggers добавляют снимки строк в Outbox, но переходы между режимами, начальный merge и разные реализации записи создают дополнительные состояния.

Предлагается выбрать один источник истины для подтверждённых операций и использовать Outbox как надёжный журнал доставки на вторую БД.

## Решение

**Рекомендация: вариант B**, при условии проверки постоянства диска Enzonic, доступности SQLite-файла всем процессам приложения и наличия только одного логического write authority. SQLite на постоянном диске Enzonic — единственный источник подтверждённых записей. Все reads бизнес-данных приложения также читаются из SQLite. PostgreSQL в США принимает изменения только от репликатора Outbox и служит удалённой копией для аварийного восстановления, аналитики или иных явно read-only задач.

Пользовательская запись получает подтверждение после успешного commit SQLite. Доставка в PostgreSQL асинхронна и не входит в пользовательскую транзакцию. Пока PostgreSQL недоступна, приложение принимает записи в SQLite и накапливает Outbox. Синхронизатор повторяет доставку после восстановления связи.

Это решение обеспечивает подтверждение без сети до США, но само по себе не обеспечивает высокую доступность при отказе Enzonic или его диска. Для этого нужен отдельный механизм восстановления/репликации SQLite и проверенная резервная копия.

## Фактическая область изменений

Изучены `database.py`, `database_manager.py`, `db_sqlite_schema.py`, `db_sync.py`, `main.py`, `trade_requests.py`, `analytics.py` и соответствующие тесты.

Текущие runtime-таблицы и write-paths, которые должны войти в целевой контракт:

| Область | Таблицы / операции | Точки кода |
| --- | --- | --- |

### Изменяемые модули

- `database_manager.py`: убрать выбор primary DB и failover-переключение; оставить конфигурацию локального SQLite, lifecycle, блокировки и статус доставки.
- `database.py`: все публичные чтения/записи направить на SQLite; удалить штатную PostgreSQL-ветку и отдельные shadow-write пути. Каждая бизнес-запись вместе с Outbox должна проходить через одно соединение и транзакцию.
- `db_sqlite_schema.py`: сделать схему полноценной основной схемой, добавить строгие ограничения, версии схемы, журнал транзакций/outbox и необходимые уникальные ключи.
- `db_sync.py`: заменить двунаправленный sync/failover на односторонний SQLite→PostgreSQL dispatcher; добавить lease/claim, повторную доставку и метрики лага.
- `trade_requests.py`: переходы и перенос двух сторон обмена выполнять одной SQLite-транзакцией с одним `transaction_id`; убрать прямые соединения и зеркалирование PG→SQLite.
- `analytics.py`: направить все записи на SQLite и включить их в Outbox/политику репликации. Если часть телеметрии сознательно не реплицируется, это оформить отдельной политикой потери данных.
- `main.py`: проверить подтверждения API, admin writes, activity и startup; пользовательский успех возвращать только после commit локальной транзакции.
- тесты: текущие failover-тесты заменить/расширить проверками односторонней репликации, atomicity и запрета прямой записи в PG.

## Контракт записи и транзакции

Любой путь изменения реплицируемого состояния обязан использовать единый repository API. Вызовы `get_pg_connection()` вне синхронизатора, startup-bootstrap и административного read-only доступа должны быть запрещены.

Для одной бизнес-операции:

```text
BEGIN IMMEDIATE (SQLite)
  проверить idempotency_key запроса, если клиент может повторить запрос
  проверить предусловия и права
  изменить бизнес-строки
  записать outbox_transaction(transaction_id, created_at, schema_version)
  записать упорядоченные outbox_events для всех изменённых строк
COMMIT
ответить пользователю подтверждением и результатом из committed state
```

Outbox-события лучше представлять как row-image изменения (`table`, первичный ключ, `before`, `after`, номер события внутри транзакции, версия схемы), а не как текущие операции «установить количество» или произвольный SQL. Это покрывает и прямые обновления, которые происходят при завершении обмена. Все события одной SQLite-транзакции должны иметь общий `transaction_id`, а PostgreSQL применяет весь набор и marker доставки одним PG-транзакционным commit. События нельзя разбивать между PG-транзакциями.

Для атомарного capture предпочтительны SQLite triggers на таблицах с реплицируемыми данными, которые пишут row-image в Outbox в той же транзакции. Триггеры должны вызывать строгую функцию с transaction ID, установленным repository-контекстом; отсутствие контекста приводит к rollback. Альтернатива — ручные записи в Outbox внутри каждой repository-функции, но тогда тест/ревью должны доказывать покрытие каждого пути. Нельзя смешивать эти два способа без единого и проверяемого контракта.

`BEGIN IMMEDIATE` сериализует конкурирующие writer-транзакции SQLite. Ограничения и бизнес-условия проверяются внутри транзакции. Ответ «успешно» отправляется только после commit. Если клиент потерял соединение после commit, повтор должен содержать idempotency key и получить прежний результат, а не применить действие снова.

## Репликация, порядок и дубликаты

1. Каждая SQLite-транзакция получает неизменяемый UUID `transaction_id`; каждое событие — уникальный `(transaction_id, event_sequence)` и `event_id`.
2. PostgreSQL хранит применённые transaction/event IDs с уникальными ограничениями. В одной PG-транзакции применяются все события группы и фиксируется `replicated_transactions(transaction_id, payload_hash, applied_at)`.
3. Повторная отправка той же группы с тем же hash становится no-op. Повтор с тем же ID, но другим hash — критический конфликт, остановка этой очереди и сигнал оператору.
4. Порядок определяется монотонной последовательностью SQLite, не временем UTC. Timestamp сохраняется только для диагностики.
5. Если один batch включает несколько транзакций, PG всё равно коммитит каждую исходную SQLite-транзакцию отдельно, чтобы сохранить атомарные границы.
6. Не применять supersede для событий бизнес-операций. Сжатие допустимо только для явно определённых производных/неаудируемых значений и не должно пересекать зависимые события. Особенно нельзя схлопывать переходы обмена или перенос карточек.
7. Ошибки соединения повторяются с backoff без потолка, который навсегда прекращает доставку. Некорректный payload/schema conflict помещается в состояние blocked/dead-letter и требует вмешательства; он не должен молча пропускаться.

Доставка — **at-least-once**, а эффект в PostgreSQL — **exactly-once по transaction_id** благодаря атомарному marker и изменениям в одной транзакции. Outbox не удаляется после доставки сразу: сохраняется ограниченный журнал/архив для аудита и восстановления; срок хранения и компактизация задаются отдельно.

## Согласованность таблиц

Нужно явно разделить:

- **реплицируемые бизнес-данные:** пользователи, карточки каталога, коллекции, желаемые карты, все состояния обменов, обработанные webhook update IDs и выбранные аналитические записи;
- **локальные служебные данные:** SQLite metadata, миграции, leases/claims, очередь Outbox, локальная диагностика;
- **внешние ресурсы:** изображения/иконки и Git-managed фикстуры, реплицируются своими текущими механизмами.

Для каждого реплицируемого table задаются primary key, FK порядок, delete semantics, schema version и способ применения. Удаление передаётся tombstone/delete event. Каталог `cards` нельзя обновлять в PG или SQLite отдельным неучтённым startup-процессом: источник каталога и его операции тоже должны иметь транзакционный репликационный путь. JSONB PostgreSQL сопоставляется с каноническим JSON в SQLite; временные метки хранятся в одном UTC формате. PostgreSQL identity/sequence после импорта выставляется выше максимального импортированного ID.

Верификация реплики сравнивает последовательность последней общей транзакции, число строк по таблицам и канонический hash по диапазонам ключей. Простая проверка наличия схемы, как сейчас, не доказывает свежесть или полноту данных. PG остаётся read-only для приложения и аналитики до достижения нужного watermark.

## Обмены карточками

Завершение обмена — одна транзакция SQLite: заблокировать/проверить заявку, проверить обоих участников и согласия, проверить код/состояние и наличие предлагаемых экземпляров, уменьшить количество у отправителя, увеличить у получателя, удалить конфликтующие элементы из `desired_cards` по бизнес-правилу, обновить `trade_requests.status` и completion timestamps, записать аудит. Если любая проверка/запись не проходит, откатывается вся транзакция.

Оба подтверждения завершения и Telegram callbacks должны быть идемпотентными. Условное изменение статуса (`WHERE status=...`) плюс проверка affected rows предотвращает двойной перенос. Уникальность входящего `processed_telegram_updates.update_id` и обработка update в одной локальной транзакции с изменением заявки предотвращает повтор webhook. Внешние Telegram-уведомления нельзя отправлять внутри DB-транзакции: для гарантированной доставки уведомлений понадобится отдельный notification outbox; повторные уведомления допустимы либо должны иметь собственный idempotency key.

В PG одна транзакция репликации должна включать все затронутые строки обоих пользователей, заявки и transaction marker. Так реплика не покажет состояние, где только одна сторона обмена уже получила карту.

## Несколько процессов приложения

Несколько процессов могут работать с одним SQLite-файлом на **одном хосте и локальном постоянном filesystem** при WAL, включённых FK, `busy_timeout`, коротких транзакциях и повторе ограниченных `SQLITE_BUSY`. Все writer-ы обязаны использовать один и тот же файл. SQLite WAL не следует размещать на сетевой файловой системе/томе с неопределёнными гарантиями блокировок.

Outbox dispatcher может стартовать в каждом процессе, но право отправки получает через lease в SQLite (`owner_id`, `lease_until`, heartbeat, fencing token) или через отдельный singleton worker. Захват batch, включая claim событий и транзакций, атомарен. Просроченный lease после падения захватывается другим процессом. PG deduplication остаётся последней защитой от повторов. Синхронизация времени не определяет порядок.

Если Enzonic запускает replicas на разных хостах/томах, каждый с собственным SQLite-файлом, этот вариант не является безопасным без единого внешнего writer coordinator или смены authoritative DB на PostgreSQL. Этот deployment факт — обязательный go/no-go пункт.

## Первоначальная загрузка и существующие данные

Текущая `initial_sync_pg_to_sqlite()` делает мягкий merge таблиц и не является протоколом cutover: нет общего snapshot watermark между всеми таблицами и конкурентными изменениями. Для перехода нужен контролируемый maintenance window:

1. Зафиксировать текущую конфигурацию, резервную копию PostgreSQL и SQLite, список таблиц и объёмы; доказать, что SQLite target persistent volume переживает перезапуск/пересоздание процесса.
2. Остановить все пользовательские и административные записи, webhook обработку и фоновые writer jobs. Дождаться активных транзакций; временно оставить приложение read-only или показать maintenance response.
3. PostgreSQL становится единственным источником snapshot. Выполнить согласованный snapshot/экспорт всех таблиц в FK-порядке в staging SQLite. Не смешивать старые локальные строки или pending Outbox с импортом; текущий Outbox сохранить отдельно для разбора.
4. Сохранить primary keys и значения ID без перенумерации. Загрузить сначала справочники и пользователей, затем коллекции, желаемые карты, заявки/обмены, webhook dedupe и аналитику. После этого выставить SQLite sequences/identity counters и проверить FK.
5. Проверить одинаковые количества и канонические checksum по всем таблицам, уникальные ключи, FK, статусы обменов, суммы количеств; отдельно сверить неприменённые/сомнительные локальные изменения. Любое расхождение блокирует cutover.
6. Атомарно переключить runtime на SQLite, включить обязательный Outbox capture, выполнить smoke/read-only checks и одну тестовую пользовательскую запись, затем проверить её событие в Outbox.
7. Только после проверки направить production traffic на новый путь. Перевести PG app-role в read-only/revoked DML; выдать DML лишь отдельному sync-role. Запустить односторонний репликатор и проверить watermark.
8. Хранить исходную PG-копию и backup без очистки в течение согласованного rollback window. Во время окна не возвращать приложение к записи в PG без обратного replay всех SQLite-событий.

**Потеря пользовательских данных предотвращается не автоматическим merge, а остановкой записи, воспроизводимым согласованным экспортом, сверкой и сохранением исходной копии.** Если обнаружены локальные SQLite-only операции, их сначала нужно сравнить с PG и классифицировать: применять, разрешать конфликт вручную или отклонять по явному правилу. Нельзя считать их менее важными только потому, что они локальны.

## Аварийное восстановление

- **Падение до SQLite commit:** SQLite откатывает незавершённую транзакцию, нет подтверждения и нет видимого бизнес-состояния.
- **Падение после commit до HTTP response:** операция сохранена и Outbox существует; клиент повторяет запрос с тем же idempotency key.
- **Падение до отправки в PG:** pending transaction остаётся в SQLite и будет выбрана после restart/lease expiry.
- **PG commit прошёл, локальный ack не записан:** повторная доставка встречает `transaction_id` marker и hash в PG, становится no-op; затем SQLite отмечает группу delivered.
- **PG недоступна:** записи продолжаются локально, растут backlog/lag метрики; лимит диска и поведение при нехватке места должны приводить к отказу записи до подтверждения, а не к потере Outbox.
- **Повреждение/потеря Enzonic-диска:** удалённая PG может отставать на весь backlog и не является нулевым RPO backup. Нужны отдельные согласованные backups SQLite/WAL, off-host копирование и регулярно проверяемый restore. Восстановление из PG допускает потерю всех ещё не реплицированных подтверждённых операций и должно явно показывать watermark/RPO.

## Запрет независимых записей PostgreSQL

- Runtime приложение не получает `DATABASE_URL`-роль с DML правами; PG credentials sync worker отделены от credentials web app.
- Для web-role отозвать `INSERT/UPDATE/DELETE/TRUNCATE` и DDL на реплицируемых таблицах; не выдавать владельца схемы приложению.
- Sync-role получает только необходимый DML и доступ к таблицам idempotency/replication metadata. Все его изменения приходят из проверенного Outbox applier.
- Админские импорты каталога, скрипты и аналитика не должны обходить SQLite. Миграции схемы выполняются отдельной deployment role и не меняют пользовательские данные.
- Если другие потребители PostgreSQL должны писать данные, вариант B требует перенести их команды в API, который сначала фиксирует запись в SQLite, либо выделить отдельную явно независимую область данных. Два write authority для одних таблиц несовместимы с этим ADR.
- DB permissions и тесты проверяют, что web process не может писать напрямую в PG, а PG не используется для подтверждения пользовательской операции.

## Сравнение вариантов

| Критерий | A. PostgreSQL основная, Outbox в PostgreSQL для SQLite | B. SQLite основная, Outbox в SQLite для PostgreSQL |
| --- | --- | --- |
| Подтверждение записи | PG commit; локальная копия не должна влиять на подтверждение. Если ждать синхронный SQLite write, снова есть неатомарная dual-write граница. | SQLite commit — единая локальная граница подтверждения. |
| Работа при потере связи США | Записи нельзя подтверждать без доступного PG; можно только read-only/cache или временный неавторитетный queue с конфликтным merge. | Полная локальная запись продолжается; Outbox копит задержку. |
| Межрегиональная согласованность | Сильная в PG; локальный cache догоняет из PG Outbox. | Локально сильная; PG eventual consistent с измеримым lag. |
| Обмены | Удобная межпользовательская транзакция при одном PG. | Транзакция локальна и атомарна; репликация всей группы сохраняет её атомарность. |
| Эксплуатация | Проще масштабировать несколько инстансов; требует доступности PG для всех writes. | Зависит от одного общего локального файла/volume, locks, backup и ограничения writer topology. |
| Риск split-brain | Низкий, если PG единственный writer. | Высокий при отдельных SQLite на нескольких хостах или при параллельных PG writes. |
| Восстановление после аварии | PG authoritative, SQLite можно заново построить по snapshot/Outbox. | SQLite authoritative, PG может отставать; потеря локального volume теряет неподтверждённый PG backlog. |
| Переход | Требует убрать прямые SQLite shadow writes; PG transactional outbox должен появляться в той же PG transaction. | Требует перевернуть все repository paths на SQLite и запретить PG bypass. |

**Вариант A — предпочтительнее**, если основное требование — отсутствие потери подтверждённых данных при отказе Enzonic/его диска или горизонтальное multi-host масштабирование. Он не даст работать с подтверждёнными write-операциями при недоступной PostgreSQL в США. При A правильный контракт: бизнес-изменение и PG-Outbox фиксируются одной PG-транзакцией; SQLite только потребитель/кэш и при ошибке обновления догоняет через durable Outbox. Нельзя обещать атомарность PG + SQLite одновременно.

**Вариант B рекомендуется здесь**, потому что исходное требование — продолжать пользовательские операции при недоступности PostgreSQL. Его ключевой риск — локальный постоянный диск становится критической частью durability и доступности; удалённая PG не заменяет синхронный backup.

## Риски и открытые условия

1. До реализации подтвердить у Enzonic гарантии: постоянный диск, один общий файл между процессами, SQLite WAL/locking на выбранном filesystem, поведение при restart/move host, backups и количество одновременно запущенных хостов.
2. Определить пользовательское поведение при заполнении диска, corrupt DB, schema conflict и долгой недоступности PG.
3. Зафиксировать список реплицируемых аналитических данных и персональных полей, retention и права доступа в США.
4. Определить RPO/RTO для отказа Enzonic и процедуру восстановления SQLite из PG с явным принятием потери backlog.
5. Текущий код содержит PG-specific SQL (`FILTER`, `ILIKE`, `ANY`, casts, `RETURNING`), SQLite-specific ветви, PG-oriented identity и независимые транзакционные вызовы; их поведение необходимо полностью покрыть целевыми интеграционными тестами.

## План реализации после принятия ADR

1. Инвентаризировать все reads/writes, таблицы, триггеры, FK, startup seeds, admin endpoints, analytics и webhook paths; составить таблицу ownership/replication policy.
2. Утвердить deployment go/no-go для локального disk и writer topology. Если условие не выполняется, выбрать A или PostgreSQL primary без failover-записей.
3. Утвердить SQLite schema, transaction/event envelope, idempotency keys, row-image trigger/context contract, canonical JSON/time representation и delete policy.
4. Переработать repository слой и направить все доменные записи, включая обмены и webhook deduplication, в атомарные SQLite transactions.
5. Переработать PG applier как единственный направленный репликатор; добавить schema/version validation, atomic per-transaction apply, deduplication, lease, retries, dead-letter и lag/checksum observability.
6. Добавить DB permission hardening, backup/restore и cutover/rollback runbooks до переключения production traffic.
7. Провести репетицию миграции на копии существующей БД, сверить таблицы и обмены; выполнить crash/restart тесты и нагрузочные тесты нескольких процессов.
8. Провести maintenance cutover с остановкой writes, full snapshot, сверкой, переключением роли доступа, затем наблюдать репликационный lag и consistency checks в rollback window.

## План тестирования

- **Атомарность SQLite:** внедрить ошибку между бизнес-изменением и созданием события; проверить, что не фиксируется ни то, ни другое. Успешный commit фиксирует оба.
- **HTTP-подтверждение:** commit failure не даёт success; потеря response после commit и повтор с тем же idempotency key не дублируют операцию.
- **Outbox/PG crash windows:** падение до отправки, PG commit до локального ack, повтор batch, одинаковый event ID с иным hash, недоступность PG, retry после restart.
- **Порядок и целостность:** несколько событий в одной транзакции, FK и delete/tombstone, сохранение transaction boundaries, checksum и watermark.
- **Обмены:** конкурентные подтверждения обоих участников, двойной callback/webhook, отсутствующая карта, недостаточное количество, ошибка на второй стороне переноса, rollback без частичного состояния, повтор после потери ответа.
- **Несколько процессов:** конкурентные increments/absolute saves/desired list/trade transition, занятый SQLite writer, dispatcher lease contention и захват lease после аварийного завершения владельца.
- **Первоначальный импорт:** все таблицы, пустые и заполненные состояния, ID/sequence, даты/JSON, FK, row counts/checksums; расхождение блокирует cutover.
- **Запрет PG bypass:** web credentials не имеют DML; поиск/тест всех PG connection callsites; попытка прямой записи получает отказ.
- **Durability/операции:** остановка/перезапуск процесса, backup с учётом WAL, восстановление копии, диск full/read-only/corruption, длительный backlog и очистка после watermark.
- **Сценарии пользователя:** сохранить коллекцию, повторное сканирование/подтверждение, количества 0 и >0, «Ищу», аналитическое событие, создание и полное завершение обмена.

Тесты запускаются на отдельной SQLite и выделенной изолированной PostgreSQL schema. Продакшн `DATABASE_URL` в тесты не передаётся. До реализации и запуска этих сценариев готовность архитектуры не считается проверенной.
