# Архитектура

## Область документа

Документ описывает компоненты по коду ветки `feature/card-counter`. Это обзор, а не полный контракт API. Маршруты и правила авторизации следует проверять в обработчиках перед изменением поведения.

## Компоненты

### HTTP-приложение — `main.py`

- Создаёт приложение FastAPI с названием `PUBG Card Scanner`.
- При запуске выполняет `startup_database()`: `init_db()`, миграцию хэшей рамок, синхронизацию каталога SQL-карточек из `load_db()` и `init_trade_request_schema()`.
- Регистрирует маршруты обменов из `trade_requests.py` через `register_trade_request_routes(...)`.
- Проверяет Telegram Mini App `initData` в пользовательских обработчиках, использующих эту проверку. Не предполагайте, что каждый маршрут требует Telegram-аутентификацию: проверяйте конкретный обработчик.
- Подключает Sentry только при наличии непустого `SENTRY_DSN`; `send_default_pii=False`.
- Содержит API-обработчики, статические маршруты и страницы интерфейса. Backend и frontend обслуживаются одним приложением на Enzonic origin `https://pubg-card.enzonic.dev`; корневой путь и API используют same-origin.

### Администрирование эталонных тестов счётчика

Вкладка «Тесты счётчика» работает с фикстурами в GitHub-ветке, заданной переменной `COUNTER_TEST_BRANCH` (по умолчанию `feature/card-counter`), а не с PostgreSQL и не с временными runtime-файлами. Чтение и изменение этих данных требуют действующей админ-сессии через заголовок `Authorization: Bearer ...`; для операций с GitHub также нужен `GITHUB_TOKEN` с правами на репозиторий.

| Метод и путь | Назначение |
| --- | --- |
| `POST /admin/counter-tests/run` | Запустить текущий детектор на сохранённых кропах; не изменяет эталоны. |
| `GET /admin/counter-tests` | Получить список сохранённых случаев и метаданные. |
| `GET /admin/counter-tests/image/{case_id}` | Получить кроп изображения для существующего случая. |
| `PATCH /admin/counter-tests/{case_id}?expected_quantity=N` | Изменить эталонное количество (1–999) и пересчитать сохранённый флаг `correct` относительно записанного `detected_quantity`. |
| `DELETE /admin/counter-tests/{case_id}` | Удалить случай из `cases.json` и удалить его изображение, если путь изображения проходит проверку. |
| `POST /admin/counter-tests` | Добавить размеченный пакет (1–50 случаев) в манифест и закоммитить изображения. |

Изменение эталона и удаление случая создают отдельные коммиты в выбранной ветке. Удаление через интерфейс изменяет Git-данные, поэтому действие следует подтверждать внимательно. Кнопка удаления скрыта не является границей безопасности: каждый endpoint повторно проверяет админ-сессию на сервере.

При добавлении нового пакета манифест ограничивается последними 500 случаями. В текущей реализации при вытеснении старых записей их изображения автоматически не удаляются, поэтому в `tests/fixtures/counter/images/` могут оставаться неиспользуемые файлы. Проверка результата требует просмотра созданного SHA/коммита и запуска регрессионных тестов; успешный ответ API сам по себе не подтверждает точность распознавания.

### Проверка каталога карт

В разделе «База карт» админки кнопка «Проверить каталог» вызывает `GET /admin/catalog-audit`. Endpoint требует админ-сессию и выполняет read-only проверку записей и локальных файлов иконок: обязательное название и хеши, наличие и читаемость иконки, точные дубликаты файлов и изображения без записи в каталоге. Для каждой читаемой иконки также запускается `_detect_counter(...)`; срабатывания помечаются как возможные счётчики с количеством и уверенностью. Это эвристика, а не подтверждение: администратор должен визуально проверить результаты, поскольку детали рисунка или оверлеи могут дать ложное срабатывание. Аудит не изменяет каталог и не отправляет изображения во внешние API.

### Распознавание — `scanner.py`

Модуль использует OpenCV, NumPy, Pillow и ImageHash. В сканировании важно различать три независимые задачи:

1. **Обнаружение геометрии карточек** — `detect_inventory_cards(...)` находит прямоугольные области на полном скриншоте и возвращает координаты, ряд и столбец.
2. **Распознавание счётчика** — `_detect_counter(card)` получает уже обрезанную карточку, анализирует область в правой верхней части, ищет знак умножения и одну/две цифры. Возвращает очищенный для хэширования кроп, количество, уверенность и диагностические данные. Если подходящий счётчик не найден, количество по умолчанию равно 1; этот результат сам по себе не подтверждает корректность обнаружения карточки.
3. **Сопоставление с каталогом** — рассчитываются хэши исходного и очищенного кропов, после чего API использует их для сопоставления с каталогом карточек.

В `scan_screenshot(...)` карточка сначала геометрически обнаруживается, затем из исходного скриншота вырезается её кроп, распознаётся счётчик и вычисляются хэши. Поля результата включают координаты, размеры, хэши, `quantity`, `duplicates`, `quantity_confidence` и `counter_debug`. Диагностический профиль отдельно измеряет время обнаружения, распознавания счётчика, расчёта хэшей и создания превью.

Сопоставление по хэшам требует совпадения минимум трёх признаков и достаточного отрыва от следующей карты. Один выбивающийся хэш допускается при совпадении как минимум двух признаков с высокой точностью; более слабый fallback сохраняет ограничение на выбросы. Неоднозначные похожие карты не назначаются автоматически.

Низкая насыщенность/серый цвет рамки не должны сами по себе отбрасывать геометрически найденную карточку: карты серой редкости могут быть настоящими картами инвентаря. При этом визуально затемнённая карта на экране наград или коллекции может быть недоступной/не принадлежащей пользователю. Геометрическое обнаружение не равно подтверждению владения — это состояние нужно проверять отдельно по размеченным скриншотам и соответствующей логике приложения.

При изменении сканера проверяйте полный путь: **полный скриншот → прямоугольники карточек → кроп каждой карточки → счётчик → хэши/сопоставление → API-ответ → отдельное подтверждение и сохранение коллекции**. Не смешивайте тест счётчика на готовом кропе с end-to-end тестом обнаружения карточек на полном скриншоте.

### Данные — `database.py`

- Подключается к PostgreSQL через `psycopg`.
- Получает строку подключения из `DATABASE_URL`; если переменная отсутствует, соединение завершается ошибкой.
- Инициализирует таблицы и индексы.
- Хранит пользователей, SQL-каталог карточек, инвентарь, список «Ищу» и отметки активности.

### Каталог карточек: файлы и SQL

Есть два связанных слоя, которые не следует путать:
- `card_hashes.json` читается через функции `load_db()/save_db()` в `main.py` и хранит данные распознавания/метаданные карточек, включая хэши.
- SQL-таблица `cards` обслуживается через `database.py`; при старте выполняется `sync_cards(load_db())`.

Перед изменением ID карточки, хэшей, иконок или синхронизации проверьте оба слоя и места, которые читают их. Не удаляйте записи только по похожему префиксу хэша.

### Обмены — `trade_requests.py`

Отдельный модуль с `APIRouter`, схемами запросов, проверкой участника заявки, переходами состояний, отправкой Telegram-уведомлений и передачей кода. Точные разрешённые переходы и побочные эффекты описывайте только после проверки серверной логики и тестов. Текст кнопки в Telegram сам по себе не доказывает, что действие разрешено сервером.

### Интерфейсы

- `index.html` — основной интерфейс Mini App.
- `admin.html` — административный интерфейс.
- `card_hashes.json` — каталог/хэши, используемые при сопоставлении карт.

При изменении интерфейса проследите действие пользователя от обработчика HTML/JavaScript через HTTP-запрос до серверной проверки, БД и обработки ответа.

## Хранилище

Основные таблицы, объявленные в `database.py`, включают:

- `users` — Telegram ID, профиль и отметки активности.
- `cards` — SQL-каталог карточек.
- `user_cards` — связь пользователя и карточки с количеством; составной ключ `(user_id, card_id)`, количество не может быть отрицательным.
- `desired_cards` — список «Ищу»; составной ключ `(user_id, card_id)`.
- `trades` — дополнительная таблица, объявленная в `database.py`.
- `trade_requests` — таблица заявок на обмен, схема которой инициализируется из `trade_requests.py`.

Наличие таблицы в схеме не доказывает, что текущий пользовательский сценарий использует её. Перед миграциями найдите все SQL-запросы к соответствующей таблице.

Функции `get_connection()` используют контекст соединения psycopg 3: при нормальном выходе транзакция фиксируется, а при исключении откатывается; соединение закрывается. Если код вручную вызывает `commit()`, учитывайте эту границу при анализе атомарности.

## Основные потоки

1. **Сканирование:** полный скриншот → обнаружение прямоугольников карточек → вырезание кропов → распознавание счётчика и расчёт хэшей → сопоставление с каталогом → API-ответ. Само сканирование `/scan` возвращает распознанные карточки; сохранение коллекции выполняется отдельными запросами подтверждения/сохранения.
2. **Коллекция:** стабильный ID пользователя и карточки → количество в `user_cards` → состояние `desired_cards` → отображение в Mini App.
3. **Обмен:** создание заявки → принятие/согласие участников → передача кода → подтверждение завершения → атомарный перенос карточек при переходе в завершённое состояние. Подробные проверки и исключения нужно сверять с `trade_requests.py`.
4. **Активность:** пользовательские запросы обновляют отметки активности; административный интерфейс отображает вычисленный статус активности.

## Проверенные эксплуатационные точки

- Backend и frontend доступны на Enzonic через `https://pubg-card.enzonic.dev`; PostgreSQL остаётся на Render и подключается через `DATABASE_URL`.
- Файл конфигурации Enzonic в репозитории отсутствует. Команда и настройки сборки/порта в панели платформы требуют отдельной проверки; зависимости перечислены в `requirements.txt`.
- В `main.py` объявлен `GET /health`, возвращающий `{"status":"ok"}`. Это проверка доступности HTTP-процесса, но не полноценная проверка всех операций БД или бизнес-логики.
- Sentry включается через переменную окружения `SENTRY_DSN`; внешний статус доставки событий надо проверять в Sentry, а не выводить из факта наличия SDK в зависимостях.

Не храните в документации значения секретов, токены или реальные пользовательские данные.
