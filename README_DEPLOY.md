# Развёртывание PUBG Cards

## Текущая схема

- Backend, frontend и PostgreSQL работают на Enzonic. Публичный origin приложения: `https://pubg-card.enzonic.dev`.
- FastAPI обслуживает frontend по `/`, админ-панель по `/admin`, API и `GET /health` на том же origin. Поэтому `API = ''` в `index.html` и `API_BASE = ''` в `admin.html` используют same-origin API и не требуют CORS.
- Приложение подключается к PostgreSQL через переменную окружения `DATABASE_URL`. Не храните DSN в репозитории и не выводите его в логи.
- Для локального резерва предусмотрена SQLite. Задайте `SQLITE_DATABASE_PATH` как абсолютный путь внутри подтверждённого постоянного тома Enzonic (например, `/data/pubg_local.db`, только если `/data` действительно смонтирован постоянно). Текущий код использует это значение и по умолчанию; временная директория для базы не подходит.
- Публичные ссылки на ресурсы приложения формируются из `PUBLIC_BASE_URL`; безопасное значение по умолчанию — `https://pubg-card.enzonic.dev`.

В репозитории нет конфигурационного файла Enzonic, поэтому фактические build/start команды, привязку порта, параметры PostgreSQL и кеширование платформы нельзя подтвердить по Git. Ожидаемая команда запуска приложения — `python3 -m uvicorn main:app`; проверьте в панели Enzonic, что настройка запуска соответствует требованиям платформы по адресу прослушивания и порту. Зависимости проекта перечислены в `requirements.txt`. Установка пакетов при каждом старте не настроена этим репозиторием; настройку build/cache можно подтвердить только в Enzonic.

В репозитории также нет проверяемой информации о гарантированном/разделяемом CPU, автомасштабировании, лимитах фоновых задач или постоянном диске Enzonic. Встречавшееся наблюдение «500 МБ из 1000 МБ» не указывает, RAM это или диск, поэтому его нельзя использовать как подтверждённый лимит. Диагностика читает доступные приложению `/proc`/cgroup значения, если они присутствуют; они описывают runtime/container и сами по себе не доказывают модель тарифа или гарантию ресурсов. Никакая искусственная CPU-нагрузка не создаётся.

Для ограничения ресурсов сканирования доступны `SCAN_CONCURRENCY` (максимум одновременных сканов, по умолчанию `1`), `CV2_NUM_THREADS` (потоки OpenCV, по умолчанию `1`), `COUNTER_MAX_CONTOURS_PER_PASS` (обрабатываемые контуры на один проход детектора, по умолчанию `64`), `SCAN_RATE_LIMIT` (запросов на один ключ за период, по умолчанию `10`) и `SCAN_RATE_WINDOW_SECONDS` (период в секундах, по умолчанию `60`). `POST /scan` ограничивает анонимных по адресу клиента и авторизованных по проверенному Telegram user ID. Загрузка ограничена 15 МБ и 30 мегапикселями.

## Диагностика сканера и локальные файлы

Диагностические события `POST /scan` записываются в JSONL в `scanner_diagnostics/` рядом с `main.py` (или в путь из `SCANNER_DIAGNOSTICS_DIR`). Это локальная файловая система процесса: в репозитории нет конфигурации Enzonic, сведений о постоянном томе либо подтверждения сохранения файлов после рестарта/деплоя. Не используйте эти логи как постоянное хранилище; сначала подтвердите свойства диска в панели Enzonic.

Файлы изолированы от пользовательских данных, имеют права создания `0600`/`0700`, ротируются по 5 МиБ и очищаются в пределах 100 МиБ/7 дней. Лимиты настраиваются переменными `SCANNER_DIAGNOSTICS_MAX_FILE_BYTES`, `SCANNER_DIAGNOSTICS_MAX_TOTAL_BYTES`, `SCANNER_DIAGNOSTICS_RETENTION_DAYS` и `SCANNER_DIAGNOSTICS_MAX_REPORT_BYTES` (10 МиБ). `SCANNER_DIAGNOSTICS_ENABLED` и `SCANNER_DIAGNOSTICS_LOCAL_STORAGE_ENABLED` позволяют отключать запись. Сбой файлового логирования не прерывает сканирование.

Логи и сводка доступны только через серверную административную авторизацию: `GET /admin/scan-logs/files`, `GET /admin/scan-logs/summary` и скачивание конкретного файла через `GET /admin/scan-logs/files/{filename}`. В админ-панели есть список файлов и прямая загрузка. Несколько worker ведут отдельные журналы; их локальные каталоги не объединяются автоматически.

Лёгкий прогрев выполняется при старте worker и может запускаться после подтверждённого Telegram heartbeat, открытия сканера или выбора файла. Сигналы не отправляют изображения и не ждут завершения прогрева. Сканирование не блокируется прогревом. Флаги: `SCANNER_PREWARM_ENABLED`, `SCANNER_PREWARM_ON_START_ENABLED`, `SCANNER_PREWARM_ONLINE_ENABLED`, `SCANNER_PREWARM_ON_OPEN_ENABLED`, `SCANNER_PREWARM_ON_FILE_SELECT_ENABLED`, `SCANNER_PREWARM_ON_SCAN_ENABLED`. `SCANNER_PREWARM_CPU_EXPERIMENT_ENABLED` по умолчанию выключен; CPU-эксперимент не реализован и не запускается даже при включённом запросе флага, поскольку политика/модель CPU Enzonic недоступна в репозитории. Доступные процессные/cgroup метрики записываются только в моменты событий и запросов; недоступные значения остаются `null`.

## Переменные окружения

Храните значения только в настройках окружения сервиса, не в Git и не в логах. В частности, необходимы `DATABASE_URL` (адрес PostgreSQL на Enzonic) и (для Telegram-функций) `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`; админ-функциям требуются `ADMIN_PASSWORD` и рекомендуется `ADMIN_SESSION_SECRET`. `PUBLIC_BASE_URL` можно задать явно, если публичный origin меняется. Для версии приложения задайте `APP_COMMIT` при сборке/деплое; если переменная не задана, приложение использует доступные `GITHUB_SHA`, `RENDER_GIT_COMMIT` или `SOURCE_VERSION`, затем пытается прочитать локальный Git SHA.

Для резервной БД предусмотрены `SQLITE_DATABASE_PATH` (путь постоянного файла; по умолчанию `/data/pubg_local.db`), `DB_FAILOVER_CONNECT_TIMEOUT` (секунды, по умолчанию `5`), `DB_FAILOVER_CHECK_INTERVAL` (секунды, по умолчанию `30`), `DB_SYNC_RETRY_DELAY` (базовая задержка повторов, по умолчанию `10`), `DB_SYNC_MAX_RETRY_DELAY` (потолок backoff, по умолчанию `900`) и `DB_SYNC_MAX_ATTEMPTS` (по умолчанию `10`). Эти значения не подтверждают, что путь `/data` является постоянным или доступным всем workers.

### Статус PostgreSQL + SQLite

SQLite включена в режиме WAL; её файл и sidecar-файлы `-wal`/`-shm` должны находиться на одном постоянном томе. Для консистентной резервной копии используйте SQLite Online Backup API (`sqlite3.Connection.backup`) либо checkpoint с остановленными writers; обычное копирование только `.db` во время работы не считается корректным бэкапом. В текущем репозитории нет конфигурации backup-процесса Enzonic или подтверждения, что этот путь попадает в ежедневные копии/S3 — это надо проверить до production.

На данный момент failover/outbox — незавершённая реализация. Часть операций инвентаря, wishlist, аналитики и webhook-дедупликации журналируется, но переходы заявок на обмен и изменения количества карт при завершении обмена не имеют полного идемпотентного журнала; первичная загрузка и возврат на PostgreSQL не сравнивают полное содержимое строк, а только таблицы/счётчики. Конфликт независимых изменений PostgreSQL и SQLite надёжно не разрешается. Поэтому не включайте эту ветку в production и не считайте автоматическое переключение безопасным до закрытия этих ограничений и проверки конфигурации тома/workers/backup. Резервный запуск требует маркер `postgres_snapshot_complete`, который записывается только после успешной первичной загрузки PostgreSQL и проверки внешних ключей; пустая или неподтверждённая локальная база не считается безопасной копией.

## Telegram

Код принимает webhook на `POST /telegram/webhook`, сверяет `X-Telegram-Bot-Api-Secret-Token` с `TELEGRAM_WEBHOOK_SECRET` и использует `TELEGRAM_BOT_TOKEN` для вызовов Bot API. Кнопка Telegram Mini App открывает `PUBLIC_BASE_URL`. Наличие маршрута в исходном коде не подтверждает регистрацию webhook в Telegram — проверяйте её отдельно в безопасном канале, не публикуя URL с секретом.

## Проверка после изменения

1. Проверьте ветку, SHA коммита и состав diff.
2. Убедитесь, что Enzonic собрал и запустил нужный SHA; настройки сервиса в панели не подтверждаются этим репозиторием.
3. Проверьте `GET /health` и пользовательские сценарии. Health endpoint подтверждает доступность HTTP-процесса, но не исправность операций с БД, авторизации, сканирования или обменов.
4. Проверьте same-origin frontend/API, ссылки изображений и Telegram Mini App.
5. Убедитесь, что PostgreSQL на Enzonic доступен приложению через заданный `DATABASE_URL`; не запускайте destructive SQL для проверки деплоя.
6. Проверьте GitHub Actions для соответствующего SHA: текущий CI-статус требует проверки в GitHub Actions и не подтверждается наличием workflow-файлов. Успешный деплой не доказывает прохождение тестов.

Не удаляйте записи или файлы данных вслепую: сначала определите источник и подтвердите тестовый характер затрагиваемых данных.
