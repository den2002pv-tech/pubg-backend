# Развёртывание PUBG backend

Этот файл описывает текущий путь развёртывания по проверенной конфигурации Render. Настройки Vercel и внешних интеграций могут меняться отдельно — перед операциями сверяйтесь с панелями сервисов.

## Render Web Service

Текущая конфигурация сервиса `pubg-backend`:
- Репозиторий: `den2002pv-tech/pubg-backend`.
- Ветка: `feature/card-counter`.
- Команда сборки: `pip install -r requirements.txt`.
- Команда запуска: `uvicorn main:app --host 0.0.0.0 --port $PORT`.
- Проверенный health endpoint в коде: `GET /health`, ответ `{"status":"ok"}`.

Секреты и значения переменных окружения хранятся в Render Environment, а не в Git. Для запуска приложения требуется `DATABASE_URL`. Пользовательские функции используют Telegram `TELEGRAM_BOT_TOKEN`; админ-панель использует `ADMIN_PASSWORD` и подпись сессии на основе `ADMIN_SESSION_SECRET` (если секрет сессии не задан, код использует пароль как fallback). Для Sentry задаётся `SENTRY_DSN`; трассировку можно настроить через `SENTRY_TRACES_SAMPLE_RATE`.

## Проверка после изменения

1. Убедитесь, что коммит находится в ожидаемой ветке и содержит только необходимые файлы.
2. Дождитесь автоматического деплоя Render для этого коммита.
3. Проверьте, что деплой завершился успешно и сервис запущен.
4. Откройте `/health` и убедитесь, что возвращается `{"status":"ok"}`.
5. Проверьте соответствующие пользовательские сценарии и логи. Health endpoint подтверждает доступность процесса, но не правильность сканирования, авторизации, обменов или транзакций.
6. Если изменялся frontend, отдельно проверьте фактическую конфигурацию и deployment Vercel; не запускайте лишний redeploy без необходимости.

## Безопасность данных

Не удаляйте записи с пустыми или ошибочными хэшами вслепую. Сначала выясните, в каком источнике они хранятся (`card_hashes.json`, SQL-каталог или другое хранилище), определите затронутые записи и подтвердите, что данные тестовые. Предпочитайте адресное исправление с резервной копией/возможностью отката. Не загружайте конкретные тестовые изображения и не меняйте данные production только по старым заметкам.

## Ограничения

Успешный деплой не доказывает прохождение тестов или корректность бизнес-логики. После изменений проверяйте GitHub Actions для точного SHA и вручную проверяйте сценарии, которые не покрыты автоматическими тестами.
